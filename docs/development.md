# Current State: What's Actually Implemented and Running

This is the single canonical account of what is built and running today. [`overview.md`](overview.md), [`architecture.md`](architecture.md) and the top-level [`README.md`](../README.md) point here instead of restating these facts.

## Firmware: `yocto-superbird`

The device runs `yocto-superbird` with this project's overlay: `aarch64-unknown-linux-gnu` userspace, systemd-managed services and a Chromium 147 kiosk (verified on the device on 2026-11-22). The image boots with the USB-C port in device mode unless a persisted Mode says host, so SSH over USB-CDC-NCM is available at boot; host mode for dock adapters is a live, persisted setting on Device settings, USB mode (details in [`hardware.md`](hardware.md#device-settings)). In the device role the NCM dev link exists even with adb off (the `thing-revived-usb-bind` recipe binds the gadget), and you reach the kiosk with `ssh kiosk@<device>` and its password. SSH, `adbd` and the UART root console are persisted settings on that screen on every build, behind the admin unlock, and `THING_REVIVED_ENABLE_ADB`/`THING_REVIVED_ENABLE_UART` are now only the first-boot seed (default `0`, off) that is reapplied to adb and uart when the image id changes. Build and flash workflow: [`yocto-build-and-flash.md`](yocto-build-and-flash.md). Dependencies: [`dependency-surface.md`](dependency-surface.md). Accounts, passwords and SSH: [`users.md`](users.md).

## Repo layout

- `controller/`: Rust daemon, binary `controller-agent`, layered as a modular monolith with ports and adapters (`domain/`, `services/`, `adapters/`, `utils/`). Bridges buttons, knob and the settings backend to the frontend over a WebSocket on `127.0.0.1:8765`.
- `daemon/`: Rust terminal agent, binary `terminal-agent`. Runs PTY sessions and relays them over a WebSocket on `127.0.0.1:8766`.
- `frontend/`: the kiosk web app. Classic scripts with no build step, a statechart interaction layer, screens defined as data, and vendored xterm.js 5.3.0 and FitAddon 0.8.0 under `frontend/vendor/`.
- `config/`: `controller.toml`, `terminal.toml` and `frontend.toml`, plus `config/protocol/` with the golden JSON wire fixtures shared by the Rust and frontend tests. See [`config/README.md`](../config/README.md).
- `build/`: `build-image.sh`, `flash-image.sh`, the Yocto overlay recipes (`build/overlay/`), config tooling (`build/tools/`) and `build/artifact/` for built images (contents gitignored). See [`build/README.md`](../build/README.md).
- `deploy/`: one legacy supervisord conf for `thing-revived-terminal`, kept for historical and stock-firmware reference only.
- `docs/`: this documentation.

Each Rust component is a plain crate at its own top-level directory. A `LICENSE` (MIT) file sits at the repo root.

## Services on the device

Two application units run on the device: `controller-agent.service` (from the `controller-agent` recipe) and `thing-revived-terminal-agent.service` (from the `thing-revived-terminal-agent` recipe). The terminal agent runs as the `kiosk` user, not root. The accounts recipe (`thing-revived-accounts`) adds `thing-revived-etc.service` (mounts the `/etc` overlay) and `thing-revived-provision.service` (boot-time account state check). Both bind loopback only, overridable with `CONTROLLER_BIND` and `TERMINAL_AGENT_BIND` (see the Security model in [`architecture.md`](architecture.md#security-model)). Their configuration is installed under `/etc/thing-revived/` (`controller.toml`, `terminal.toml`), and the frontend config is generated into the kiosk web app at image build time. The web app, including the vendored xterm.js assets, is the kiosk's default boot page (`superbird-kiosk-default-webapp` recipe), and the only client of both WebSockets is the kiosk's own Chromium 147 page.

## The terminal: `daemon/` + `frontend/`

The main deliverable: a vendored xterm.js terminal UI backed by a Rust PTY agent, with multiple live sessions, typed into from a Bluetooth-paired keyboard (pairing and typing confirmed on hardware) plus the device's buttons and knob for session chrome (next/prev session, interrupt, clear, respawn). Full design and wire protocol: [`terminal.md`](terminal.md).

## `controller/`: buttons, knob and settings backend

A live runtime dependency of the frontend, not a prototype. It reads the buttons and knob through `evdev`, grabs them (`EVIOCGRAB`) and replays session-chrome keys through `uinput`, and serves the settings-menu backend: Bluetooth (BlueZ over D-Bus), brightness, timezone and Wi-Fi. Button and knob scancodes, the grab and replay mechanism, and the Bluetooth, brightness and timezone backend are confirmed on real hardware: see [`research/button-knob-clock-design.md`](research/button-knob-clock-design.md) and [`research/hardware-verification.md`](research/hardware-verification.md).

- **Wi-Fi works on real hardware.** Verified 2026-11-22 with a D-Link DWA-171 (`rtw88_8821cu`) through a USB-C dock in USB host mode; the dock's Ethernet also works. The code is in `controller/src/domain/wifi/`, `controller/src/adapters/wpa_ctrl.rs` and `controller/src/services/wifi.rs`, with a Wi-Fi submenu in `frontend/`. The image side is the `thing-revived-wifi-config` overlay recipe (plus `thing-revived-wifi-udev`). Design, wire protocol and limitations: [`wifi.md`](wifi.md).
- **Clock sync is system NTP.** The image runs `systemd-timesyncd` (the `thing-revived-ntp-config` recipe). The daemon reports the clock status to the frontend from `timedatectl show -p NTPSynchronized`; there is no SSH probe. Verified on hardware on 2026-11-22: the clock syncs by itself once a network is up.
- **Accounts and first-boot password.** Implemented in the repo, not yet built into an image or run on a device (status: implemented, pending the first build). The image ships `kiosk` locked with no SSH key baked. If `kiosk` has no usable password, the frontend shows a full-screen "Kiosk password not set" message with an arrow at the M button. The first M press makes the controller generate and set a password and the screen shows it, with no toast and no timeout. The second M press acknowledges. A reboot before the acknowledgement locks the password again and the unset screen returns. The password lives in controller memory only, and the only stored artefact is its hash. The controller owns the phase machine (`none`, `prompt`, `generating`, `showing`, `done`) and decides at the evdev reader, so only the physical M press counts. Design: [`users.md`](users.md).
- **SSH and sudo.** `kiosk` signs in by password or by a key from the key store, with `Match User kiosk` and `AuthenticationMethods password publickey` in the sshd drop-in. Root is locked and refused, and every other user is key-only. `pam_faillock` is set to `deny=5 unlock_time=600 fail_interval=900`. The on-device unlock path verifies passwords with `unix_chkpwd`, which bypasses faillock, so the app's own rate limiter is the brake there. Terminal shells run as `kiosk` and so carry its `sudo` and `adm` groups (systemd calls `initgroups()` whenever `User=` is set). Account changes persist through an overlay on `/etc` with its upper layer on `/var`.
- **Device settings menu.** One main menu row, Device settings, replaces the old USB mode, Debug access and Users rows. Its first row is Unlock (the kiosk password, a fixed 30 minute session, `users.session_ttl_secs`) and the other rows grey out until it is unlocked. Unlocked, the rows are Users, Groups, Reboot device (hold to confirm) and USB mode, which has inline Mode (host or device, switched live), SSH, ADB and UART rows, all persisted in `/var/lib/thing-revived/device-settings.json`. Host forces ADB off and greys it. The build flags only seed the first boot, and adb and uart reseed when the image id changes. Boot apply is three small units that run `controller-agent apply-device-settings` (`controller/src/boot_apply.rs`, unit files in `build/overlay/recipes-extended/thing-revived-device-apply/`). Code: `controller/src/domain/device_settings.rs`, `controller/src/adapters/device_ctl_cli.rs`, `controller/src/adapters/device_settings_json.rs`, `frontend/src/menu/screens/device-settings.js` and `frontend/src/menu/screens/usb-mode.js`. Behaviour, boot units and recovery: [`hardware.md`](hardware.md#device-settings). To try a change on a device, cross-compile the controller (`aarch64-unknown-linux-gnu`, static CRT) and copy the binary plus the `frontend/` files over the dev link before switching to host mode, since host mode removes that link.
- **Users and Groups.** Device settings, Users and Groups, after Unlock: users (add, lock, set password, remove), groups, SSH keys, with hold-to-confirm for destructive actions. Wire protocol and error codes: [`../config/protocol/controller/README.md`](../config/protocol/controller/README.md). Defaults and limits: the `[users]` section in [`../config/README.md`](../config/README.md).
- **Persisted root surfaces.** adb and the UART root console are persisted settings, not volatile toggles: nothing reverts them when the admin session ends or on reboot, so they can survive on a prod image until switched off, reseeded by an image id change or wiped by a factory reset. The security statement is in [`users.md`](users.md#security-notes-and-accepted-limits).
- **Scope.** No smart-home or Bluetooth-peripheral client is part of this project; `controller/Cargo.toml` has no such dependency. The terminal and settings menu are the deliverable.

## Image layout and baked tools

All statements in this section come from host tests and from reading the recipes. No image with these changes has been built and none has been flashed, see [Not yet verified](#not-yet-verified).

- **Partition layout.** The wic has five partitions in this order: `env` 8 MiB, `boot_a` 64 MiB, `root_a` 770 MiB, `boot_b` 64 MiB and `root_b` 770 MiB (upstream's root slots are 516 MiB). There is no `bandaid` partition and no `data` partition in the wic: `data` is carved at first boot from the tail of the eMMC. The project wks `superbird-mainline-nobandaid.wks.in` is upstream's file minus the bandaid line, under a distinct name so upstream's file does not shadow it. The OTA headroom check needs `data` to be at least `boot 64 + root 770 + margin 64` = 898 MiB, and on paper the floor is about 1924 MiB (3600 MiB minimum eMMC minus 1676 MiB of fixed partitions), so it passes. The wic fixed total is 8 + 2*64 + 2*770 = 1676 MiB. This 770 MiB layout has not been built yet; the first real build used 650 MiB root slots (see [Measured numbers from the first build](#measured-numbers-from-the-first-build)).
- **Build flags.** `build/build-image.sh` writes `SUPERBIRD_ROOT_PART_SIZE = "770"` and `SUPERBIRD_BANDAID_PART_SIZE = "0"` into the generated kas file. The second value only makes the headroom check count the real layout, since the prod image bbappend already drops the bandaid line from the wks and `superbird-kiosk-bandaid` from `EXTRA_IMAGEDEPENDS`. Never build the bandaid recipe with size 0.
- **Bandaid removal.** The bandaid partition and the upstream placeholder daemon (`superbird-kiosk-daemon`, `/opt/superbird-kiosk`) are gone from the image. A rootfs post-process strips the `PARTLABEL=bandaid` line from `/etc/fstab` and fails the build if the word survives.
- **Data guard.** `thing-revived-data-guard.service` runs once per boot, after `superbird-provision.service` and before the data fsck, the makefs instance for `PARTLABEL=data`, `var.mount` and `local-fs.target`. If the data partition carries an ext4 labelled `bandaid`, it wipes that signature so `x-systemd.makefs` formats the partition fresh instead of mounting a stale 192 MiB filesystem as `/var`. This case arises after a re-flash from the old layout, where the new `data` partition starts at the byte offset of the old bandaid filesystem. A filesystem with any other label, or none, is left alone, a mounted device is left alone, and the script exits 0 on every path so it cannot block boot. The prod image bbappend fails the build if the unit, the script or the enablement link is missing.
- **Baked tool set.** The prod image bbappend installs: `curl`, `vim` (with `vim-common`, `vim-vimrc`, `vim-syntax`), `nano`, `htop`, `tmux`, `procps`, `ncurses-tools`, `file`, `jq`, `less`, `ncdu`, `rsync`, `bash-completion`, `iproute2` (with `iproute2-ip`), `iputils-ping`, `ethtool`, `usbutils`, `strace`, `lsof`, `tcpdump`, `python3-core`, `python3-pip`, `python3-setuptools`, `python3-ensurepip`, `evtest`, `i2c-tools`, `mmc-utils`, `libgpiod-tools`, `util-linux-lsblk`, `util-linux-findmnt`, `systemd-analyze` and `ldd`. `vim-help` and `vim-tutor` are dropped through `BAD_RECOMMENDATIONS` to save space. Updates arrive only with a new image, see [`pkg-manager.md`](pkg-manager.md) for the package manager options, the decision is still pending.
- **BusyBox applets shadowed.** `procps`, `iproute2`, `iputils-ping`, `vim`, `less` and `ncurses-tools` ship the full tools in place of the matching BusyBox applets (`ps`, `top`, `free` and friends, `ip`, `ping`, `vi`, `less`, `clear` and `tput`). Which applet symlinks the packages displace through update-alternatives, and which BusyBox applets remain, is unconfirmed until an image is built. Other applets, and the BusyBox quirks noted in [`yocto-build-and-flash.md`](yocto-build-and-flash.md), are unchanged.
- **Fonts dropped.** A `chromium-kiosk` bbappend removes `noto-sans-cjk` and `noto-color-emoji` from the recipe's `RDEPENDS`, about 36 MiB. The frontend only needs Latin glyphs and a few symbols, which `liberation-fonts` covers. Side effect: CJK and emoji characters in Wi-Fi SSIDs, Bluetooth names and terminal output render as tofu.
- **Terminal TERM.** `[pty] term` in `terminal.toml` (default `xterm-256color`, must not be empty) is the `TERM` for every session, and `COLORTERM=truecolor` is set with it. It applies only when the terminal agent itself has no real `TERM`, meaning unset, empty or `dumb`. Neither the agent nor its unit sets `TERM`, so before this bash fell back to `dumb` and `clear` and `htop` broke. Covered by two daemon unit tests, not seen on a device.
- **Checker invariants.** `python3 build/tools/check_image_accounts.py <built .wic> --manifest <image .manifest>` now also fails on: a wic layout that is not exactly the five partitions and sizes above in that order, any `bandaid` partition, less than the OTA headroom left for `data`, `root_a` content over a 640 MiB used budget (the 770 MiB slot minus 130 MiB of growth margin), either dropped font package or font file present, any baked tool package missing or `vim-help` or `vim-tutor` present, bandaid leftovers (the fstab line, `superbird-kiosk-daemon`, `/opt/superbird-kiosk`), and a missing or disabled data guard unit or script. The tool and font package checks need `--manifest` because the image has no opkg status file. Without either the checker reports that it has no installed package list and fails.
- **Geometry change forces a full flash.** Changing the partition sizes, as this change does, needs a full flash, and a full flash wipes `/var`: the kiosk password, Device settings (`device-settings.json`), the `/etc` overlay's upper layer and the SSH host keys. After it the device is in the first-boot state again (password screen, new host keys, so SSH clients warn). Burn-mode flashes with an unchanged geometry keep `/var`, as before. A device flashed with the older 516 MiB root layout will lose `/var` on reflash, as will one flashed with the interim 650 MiB layout.

### Measured numbers from the first build

The first real build used 650 MiB root slots. The 770 MiB layout has not been built yet, so none of the 770 figures are measured.

- **Root content.** `root_a` content measured 571.7 MiB. In a 770 MiB slot that leaves 198 MiB of headroom, about 26%, which is an arithmetic projection and not a measurement.
- **Wic layout.** Five partitions: `env` 8 MiB, `boot_a` and `boot_b` 64 MiB each, `root_a` and `root_b` 650 MiB each (first build). The next build uses 770 MiB root slots.
- **Flash zip.** 419 MB without `bandaid.ext4`.
- **Largest package additions.** Measured pkgdata sizes, not installed-on-disk sizes: `vim-common` 17.9 MiB, `file` 10.4 MiB, `python3-core` 10.2 MiB, `python3-pip` 9.9 MiB, `python3-setuptools` 6.9 MiB, `vim` 4.7 MiB.

## Known limitations

- Chromium runs as root with `--no-sandbox`, `--single-process` and a loopback debugging port, see [`hardware.md`](hardware.md).
- Password SSH gives single-factor remote root through `kiosk` and `sudo`.
- If the `/etc` overlay fails, the device has no remote access (degraded mode).
