## 1. Runtime Options

### 1.1 Chromium / CEF kiosk status

**Confirmed, primary source (GitHub repo content, high confidence):** `yocto-superbird`'s own README (re-fetched this pass, post-dating the version quoted in `research.md`) now lists **`superbird-kiosk-prod-image`** and **`superbird-kiosk-dev-image`** as first-class, maintained image variants: "ext4 ro rootfs, chromium kiosk, example daemon, placeholder webapp" (prod) and "squashfs-lz4 rootfs, weston desktop + VNC + dev tools" (dev). This is a materially new fact vs. the state of the project described in `research.md` §2.2: Chromium kiosk is no longer just a roadmap item teased in the r/carthinghax announcement title ("yocto-superbird: bluetooth, chrome 147, gpu..."), it is a shipped, forkable template (`examples/meta-superbird-kiosk-example/`), and it is the base for the author's own production product (`bridgething-{prod,dev}-image`, same Chromium-kiosk pattern).

**Not confirmed in this pass:** whether this Chromium build is GPU-accelerated or software-rendered, and what FPS/responsiveness it gets on a non-trivial page (a smart-home-controller-style dashboard or a React SPA). The announcement reddit thread title explicitly pairs "chrome 147" with "gpu" as a bullet, implying the author is claiming *some* GPU work, but the full post body could not be retrieved in this research pass (Reddit and the pullpush/Unddit mirror both failed to fetch). **This specific question, is yocto-superbird's Chromium kiosk GPU-accelerated in practice, is an open question; do not assume yes or no.** Recommend: build the `superbird-kiosk-dev-image`, load `chrome://gpu`, and read the Graphics Feature Status table directly (see §1.2 for why this is architecturally plausible either way).

**Confirmed, primary source (high confidence):** `bishopdynamics/superbird-debian-kiosk` ("Wall Thing") explicitly lists **GPU acceleration: Not working**, with the stated reason: "the hardware has a Mali GPU, but the stock OS uses it via DirectFB QT library, and does not include necessary libraries to make it work with X11." It runs Chromium on a software-rendered X11/framebuffer stack. No quantitative FPS/latency numbers for a dashboard-class page were published anywhere found in this research (the YouTube walkthrough and the Reddit "Turned my Car Thing into a smart-home kiosk" thread describe it as functional/"not that [fast]" qualitatively, not measured). **Treat perceived performance on this specific image as "usable for simple dashboards, unquantified, likely sluggish for anything graphically heavy" rather than a hard number.**

**New data point found this pass, not in `research.md`:** a comment on the `superbird-debian-kiosk` announcement issue (err4o4 repo, Jan 2024) states: *"newer versions of the car thing OS actually use chromium on top of Wayland so if you can get xwayland working that might be good."* This claims **stock Spotify firmware itself moved to a Chromium+Wayland app runtime in later OS updates**, which would be new information relative to `research.md` §8.8's conclusion that stock firmware is Qt+EGLFS (that conclusion was sourced to an Oct 2022 writeup against App Version 0.24.107, an early build). **Confidence: low**, this is a single secondhand forum comment, not independently verified against a specific later stock firmware version/build number, and it directly contradicts the primary-sourced §8.8 finding for the version actually inspected. Flag as **unconfirmed and in tension with existing research**, not as a correction; do not treat it as settled either way without a version-matched primary source (teardown of a *later* OS build specifically).

### 1.2 Resolving the GPU tension: is acceleration available on this hardware at all?

This is the key question the user asked to resolve, and the research does resolve it:

**The GPU silicon is real and modern enough to matter.** The S905D2 (per `linux-meson.com`, the canonical Amlogic-mainlining community reference, and corroborated by Wikipedia's Mali-processor SoC table) pairs with a **Mali-G31 MP2**, a Bifrost-generation GPU supporting OpenGL ES 3.2 and Vulkan 1.0. **Confidence: high**, cross-checked across two independent sources.

**Mali-G31 has a working open-source mainline driver path.** The Mesa **Panfrost** driver supports Bifrost-family GPUs including the G31, through the mainline kernel's `drm/panfrost` DRM/KMS driver, confirmed by a direct hobbyist report (Manjaro ARM forum) of Panfrost running accelerated on an **X96Max+ TV box with the same SoC family and the same Mali-G31**, with `glxinfo` showing "direct rendering: Yes," vendor string "Panfrost," on a mainline-ish 5.9 kernel. This is not Car Thing-specific, but it is the same GPU core on the same SoC family, under mainline Linux, which is exactly the situation `yocto-superbird`'s mainline v7.x kernel puts the device in. **Confidence: medium-high** (direct hobbyist report on the same GPU/SoC family, not a Car-Thing-specific confirmation).

**This resolves the apparent tension the user flagged:** Qt+EGLFS working in *stock* firmware does not mean the kiosk projects "just haven't wired up" the same path, it means two different kernels are in play:
- **Stock firmware** (Amlogic OpenLinux/Buildroot, per `research.md` §8) almost certainly uses Amlogic's **closed-source vendor Mali driver** ("libmali" blob + vendor `mali_kbase`/`mali` kernel module, this is Amlogic's standard shipping driver for this GPU family, per the `hexdump0815` Amlogic-kernel reference found in this pass), accessed directly by Qt's EGLFS platform plugin via DRM/KMS with no X11/Wayland compositor in the way. This is architecturally the easiest path to get GPU accel working, no window-manager integration needed, which is exactly why Spotify's own single-purpose native app could use it.
- **`superbird-debian-kiosk`** inherits the **stock Amlogic kernel** (per `research.md` §2.5, it's explicitly the stock kernel + Debian 11 rootfs) but tries to run Chromium through **X11**, and the vendor Mali blob driver's X11 (EGL/GLX) userspace libraries are not present/wired into that Debian rootfs, hence "GPU acceleration: not working" is a true statement about *that specific OS image's packaging*, not about the silicon. The GPU is there; the glue (vendor blob's X11 EGL libs, or a Panfrost-capable mainline-ish kernel) simply isn't assembled in that project.
- **`yocto-superbird`** runs a genuinely **mainline v7.x kernel** (not the stock Amlogic kernel), which is the situation where Panfrost (the open-source Mesa driver) becomes a realistic path to DRM/KMS-direct GPU acceleration for Chromium's Ozone/DRM or Ozone/Wayland backend, **but whether `yocto-superbird`'s specific kernel config and `meta-chromium`/`meta-browser` layer choice actually enables this was not confirmed in this pass** (the README doesn't spell it out, and the announcement post couldn't be read in full). This is the single most valuable thing to verify empirically before committing architecture, see §3.

**Bottom line on the user's specific question:** yes, Qt+EGLFS working in stock firmware is real evidence the Mali-G31 GPU is physically present, DRM/KMS-capable, and already exercised by production Spotify code. It does **not** automatically mean any given community kiosk image has GPU acceleration wired up for Chromium; that depends independently on (a) which kernel that image runs (stock vendor kernel vs. mainline) and (b) whether the Mesa/Panfrost or vendor-blob EGL stack is actually linked into that image's Chromium/X11/Wayland packaging.

**Correction (2026-11-22): the "chrome 147" claim below describes the upstream yocto-superbird build and does NOT apply to this device. The owner confirms the on-device kiosk runs Chromium 68, so the GPU/modern-engine conclusions drawn here are not established for this hardware.** **Update (2026-11-16): this is no longer an open question.** The project's own site, bridgething.com (same author as `yocto-superbird`, built on it), states directly: "mainline linux 7.0.2, mainline u-boot, chrome 147, mesa + panfrost graphics for full acceleration," and lists as a feature-table row "panfrost gpu acceleration | first on superbird | open mesa drivers for the mali g31." This is a primary source (the project's own page, not an independent benchmark) confirming `yocto-superbird`'s Chromium kiosk *is* GPU-accelerated via Panfrost/Mesa on the Mali-G31, exactly the outcome reasoned about as "architecturally plausible" immediately above, now corroborated rather than merely plausible. **Confidence: medium-high** (official project page, no independent FPS/latency numbers given, and it describes the `bridgething` product build specifically, whether the generic `superbird-kiosk-*-image` example inherits identical Panfrost wiring was not independently re-checked here).

### 1.3 QtWebEngine as an alternative embedding target

**QtWebEngine is a real, standard, well-documented Qt module** (Qt's Chromium-based web-rendering widget, the thing that would let the user build a React/Angular SPA and have it rendered inside a native Qt shell with a JS-to-C++ bridge via `QWebChannel`). Cross-compiling it via a Yocto-generated SDK is a documented, common pattern, the Kynetics technotes guide and Qt's own "Configure an Embedded Linux Device" docs describe exactly this workflow (Yocto `populate_sdk` + Qt's device-specific `mkspec`), and it explicitly supports the EGLFS platform plugin backend Qt uses on embedded boards with a GPU and no window manager, the same backend confirmed in stock firmware (`research.md` §8.8). **Confidence: medium-high** that this is generically feasible (strong secondary sources on the Qt/Yocto cross-compile pattern); **not found anywhere in this research**: any community report of someone actually running QtWebEngine specifically on a Car Thing/superbird device. **This is unconfirmed on this exact hardware, flag as a real gap, not a known-working path**, and note that QtWebEngine is itself a Chromium embedding (it bundles a full Chromium rendering engine under the hood), so whatever RAM/CPU concerns apply to a Chromium kiosk largely apply here too, just wrapped in a lighter native shell around it rather than a full browser UI.

### 1.4 Electron

**No community report of anyone running Electron on a Car Thing/superbird device was found.** This is consistent with the device's constraints: Electron bundles a full Chromium + Node.js runtime and in practice needs meaningfully more than the "chromium alone" footprint the kiosk projects already describe as resource-constrained on this hardware (general guidance, e.g. the `AnotterKiosk` GitHub issue thread, explicitly calls 512 MB "not recommended" for plain Chromium kiosk use without low-end-device tuning, Electron adds Node's own runtime overhead on top of that). **Confidence: high that no one has published doing this; reasonable engineering judgment, not a sourced device-specific test, that it would be materially worse than plain Chromium on 512 MB.** Not recommended for this project.

### 1.5 Node.js / npm on-device, for a local web server

- **On a Debian-based image (`superbird-debian-kiosk`):** trivial. Debian's own repos ship `nodejs`+`npm` as ordinary `apt` packages for `arm64`/`armhf` across Bullseye (11), Bookworm (12), and Trixie (13) (confirmed via `packages.debian.org` and multiple install guides). `apt install nodejs npm` would just work on this image's rootfs, same as any other Debian ARM board. **Confidence: high.**
- **On `yocto-superbird`:** Yocto has a generic `meta-nodejs`/`nodejs` recipe ecosystem (via OpenEmbedded layers), but **no evidence was found that `yocto-superbird` specifically includes or has tested a Node.js recipe in its own layer set** (`meta-superbird`, `meta-bridgething`, the kiosk example). This would need to be added as a bitbake recipe/layer dependency by the user if they went the Yocto route and wanted an on-device Node process (e.g., serving the built SPA locally rather than embedding it as static files in the Chromium kiosk's data dir). **Confidence: medium that this is possible (Yocto's node recipes are mature and widely used elsewhere); unconfirmed specifically for this BSP.**
- **Practical note:** for a React/Angular SPA, a local Node server is usually *unnecessary complexity* — but the "load directly from a local file path" option named below needs a caveat, not a blanket equivalence to a static server. **Update (2026-11-16):** a production React/Angular build loads reliably from a local `file://` path only if it is a **classic, non-module** bundle (`<script src="...">`, no `type="module"`). Modern bundlers (Vite, current Angular CLI) emit ES module script tags by default, and per the HTML spec and MDN, module scripts require strict Content-Type (JS MIME type) enforcement that a `file://` load never satisfies (confirmed by a long-standing, still-open Chromium bug, Chromium engineers describe `file://` module-script support as "intentionally not supported... for production use cases"). A default modern SPA build will silently fail to load at all over `file://`; only a tiny static file server (`busybox httpd`, already present per `research.md` §8.7's BusyBox inference, or Python's `http.server`, given Python's near-certain presence per `research.md` §4.3) — or a non-module/IIFE build target, as this project ultimately shipped — reliably serves either bundle shape. Reach for Node-on-device only if the architecture specifically needs a local API/WebSocket bridge process written in JS rather than the Python daemon already proposed in `research.md` §4.3.

**On the Chromium-69-specific coupling this pin created (moved here from the old `dependency-surface.md`):** the real, permanent pain point this created was the stock firmware's on-device Chromium 68 (2018; recorded as 69 in earlier research, corrected 2026-11-22): Spotify never once upgraded it across the device's entire OTA history, and no official newer Chromium build exists for that device's 32-bit-ARM-with-glibc architecture, a configuration Google doesn't ship prebuilt binaries for, so that version was effectively permanent short of a from-scratch Chromium cross-compile with no known working precedent. This project's own code carried two coupling points to that specific version, both now moot once the project moved onto the `yocto-superbird` reflash's newer Chromium kiosk build: a non-module IIFE bundle (needed because a plain `file://` page load never gets a `Content-Type` header, and Chromium enforces strict MIME-type checking for `type="module"` scripts regardless of version, per the update above), and the now-removed NOC dashboard frontend's use of `XMLHttpRequest` instead of `fetch` when reading its metrics file over `file://` (`Response.status` is always `0` for `file://` URLs on that Chromium version, making `Response.ok` permanently `false`). Vite/React's default build output targeting a baseline newer than Chromium 69 regardless of module-vs-IIFE bundle format compounded this, requiring an explicit `build.target: 'chrome69'` even with the non-module bundle shape.

## 2. Cross-Compilation: What Actually Needs It

**Key distinction to give the user directly: the React/Angular app's own build is never cross-compiled.** `npm run build` (Vite/webpack/Angular CLI) produces plain JS/HTML/CSS bundles, these are architecture-agnostic by construction; the exact same build artifact runs on an x86 laptop's Chrome and an aarch64 Car Thing's Chromium. **There is no cross-compilation step for the frontend code itself, regardless of which architecture below is chosen.**

What *does* potentially need cross-compilation or a prebuilt target binary is **whatever renders that bundle on-device**, and any **native bridge code** connecting hardware input to the app:

| Component | Needs cross-compile? | Notes |
|---|---|---|
| React/Angular SPA build output | **No** | JS/HTML/CSS, same artifact everywhere |
| Chromium (kiosk browser) | **No, if using a prebuilt image.** `yocto-superbird`'s `superbird-kiosk-*-image` already ships Chromium prebuilt as part of the BSP build; the user doesn't compile Chromium themselves, they build/flash the image | Compiling Chromium from scratch is a different, much heavier task (hours of build time even with Yocto's sstate cache), only relevant if patching Chromium itself, not for just using it as a kiosk |
| QtWebEngine shell (if chosen, §3a) | **Yes** | Qt/C++ app, needs an aarch64 cross-compiler + Qt's embedded-Linux device mkspec; standard Yocto `populate_sdk` output provides exactly this (see below) |
| Evdev-to-backend bridge daemon | **Depends on language** | Python: **no** cross-compilation, ships as source + runs against whatever Python interpreter is on-device (same reasoning as `research.md` §4.3's Python recommendation, this still applies and is reinforced by this pass's findings). Rust/Go/C: **yes**, needs a cross toolchain, same one used for any other native component |

### 2.1 Yocto SDK generation: confirmed standard mechanism

**Confirmed, high confidence (generic Yocto documentation, multiple independent sources, Yocto Project's own SDK manual, NXP/Toradex/RDK community docs, all describing the identical mechanism):** any Yocto-based image (which `yocto-superbird` is, by construction, it's a `kas`/BitBake-driven BSP) can produce a **self-contained cross-toolchain installer** via `bitbake <image> -c populate_sdk`, which emits a `.sh` installer bundling the cross-compiler, matching sysroot, and headers/libs for exactly the target image's package set. This is not something `yocto-superbird`'s own README documents by name in the version fetched this pass (no `populate_sdk` command appears in the README's Build section, which only shows `just build`/`just flash`), but it is a **generic property of any valid Yocto/BitBake project**: if `just build` successfully produces `superbird-bsp-image` or `superbird-kiosk-prod-image`, the identical BitBake invocation with `-c populate_sdk` against the same recipe will produce an SDK, because this is core BitBake/OpenEmbedded machinery, not an opt-in feature a BSP author has to specially wire up. **Confidence: high** that this works as a mechanism; **unconfirmed** whether `yocto-superbird`'s `Justfile` already wraps it in a convenience target (not found in the README), the user may need to invoke `bitbake -c populate_sdk <image>` directly inside the `kas-container` shell rather than via a documented `just` recipe.

### 2.2 The Debian/superbird-debian-kiosk alternative

For **`superbird-debian-kiosk`**, there's no Yocto SDK concept, it's a Debian 11 rootfs. Cross-compiling a native app for it means a manual aarch64 cross-toolchain (e.g., Debian's `crossbuild-essential-arm64` package, or a `qemu-user-static`+`debootstrap`/`multistrap` chroot to build/test natively "as if" on an aarch64 host, or just building directly *on* the device over SSH since it's a full Debian userland with real `apt`/`gcc` available, slower but zero cross-compile setup). This is the path the user may find "easier if less native," exactly as the task brief anticipated, it trades Yocto's integrated SDK generation for Debian's much lower learning curve, at the cost of the GPU/kernel-version tradeoffs discussed in §1.2.

### 2.3 What this means concretely for the user's plan

- If they write the SPA in React/Angular: **zero cross-compilation**, full stop, regardless of target OS.
- If they stick to a Chromium-kiosk shell loading that SPA (no custom native rendering shell): **zero cross-compilation for the rendering engine either**, they're consuming a prebuilt Chromium from the chosen BSP's image build, not compiling their own.
- If they build a custom QtWebEngine native shell (§3a) for tighter hardware-input integration: **yes, cross-compilation is required**, but it is a solved, documented problem via Yocto's `populate_sdk`, not a from-scratch toolchain project.
- If the evdev-to-backend bridge daemon stays in Python (as `research.md` §4.3 already recommends): **zero cross-compilation** for that piece either, on either OS base, since Python ships/installs on both without per-app compilation.

## 3. Practical Architectures, Ranked by Feasibility/Effort

### (a) QtWebEngine native shell + QWebChannel bridge: most "proper," most cross-compile work

A small Qt/C++ application (cross-compiled via the Yocto `populate_sdk` toolchain, §2.1) that:
1. Loads the React/Angular build output into a `QWebEngineView`.
2. Reads `/dev/input/eventN` for knob/buttons/touch directly in native code (or shells out to the Python evdev reader from `research.md` §4.3 and receives normalized events over a local socket).
3. Exposes those events to the SPA's JS runtime via `QWebChannel` (a documented Qt mechanism for native-to-JS object/method bridging, no polling, no local HTTP round-trip for input events).

**Pros:** Tightest possible native integration; input events can reach the SPA with no network/IPC-over-HTTP hop; reuses the exact rendering technology (`EGLFS`) already confirmed working with GPU access in stock firmware, so if `yocto-superbird`'s DRM/KMS stack is sound, this has the best shot at being GPU-accelerated by inheriting Qt's EGLFS path rather than depending on Chromium's own Ozone/DRM wiring being correctly configured in that BSP.
**Cons:** Requires Qt/C++ development + cross-compilation workflow (toolchain setup, even though it's "solved," is still a real time cost for a team used to pure web development); QtWebEngine is itself a Chromium embedding, so it inherits roughly Chromium-kiosk-class RAM usage, just packaged differently; **zero confirmed community precedent on this exact device** (§1.3), the user would be the first to validate this path on superbird hardware, meaning real risk of hitting an unknown blocker (missing EGL/Wayland platform plugin packaging in whatever Yocto layer provides QtWebEngine, etc.).
**RAM headroom:** QtWebEngine's own Chromium core typically needs on the order of 150 to 250MB+ resident for a simple page (comparable order-of-magnitude to the CEF "approximately 70MB for a single page on a 500MB VM" data point found in this research, though QtWebEngine tends to run heavier than bare CEF due to additional Qt scaffolding), on 512MB total with the kernel, BlueZ stack, and the bridge daemon also resident, this is tight but not obviously impossible; **budget for swap or aggressive low-end-device Chromium flags (`--disable-gpu-compositing` fallback, `low_end_device_mode`-equivalent) as a contingency, and measure actual resident memory on real hardware before committing to this as the final architecture.**

### (b) Chromium kiosk + local-served SPA + WebSocket input bridge: least native-integration work, depends on Chromium's GPU status

Use `yocto-superbird`'s `superbird-kiosk-prod-image` (or `-dev-image` for iteration) as-is, pointed at a locally-served build of the React/Angular app (served from a tiny static file server: BusyBox httpd/Python `http.server`/nginx, not necessarily Node, per §1.5). A separate small daemon (Python, per `research.md` §4.3, zero cross-compile) reads evdev and publishes normalized events to a local WebSocket the SPA subscribes to via ordinary browser JS (`new WebSocket('ws://localhost:PORT')`), no native bridge, no Qt, no C++.

**Pros:** Minimal new engineering, reuses the already-documented kiosk image pattern directly, reuses the Python daemon design already specified in `research.md`, and the SPA's only "native hardware" dependency is a standard WebSocket client, something any React/Angular developer already knows. Fastest path to a working prototype.
**Cons:** Entirely dependent on §1.1/§1.2's open question: if `yocto-superbird`'s Chromium kiosk turns out to be software-rendered (as `superbird-debian-kiosk`'s definitely is), a React/Angular dashboard-class page may render sluggishly on a single-core-constrained software path; this needs the `chrome://gpu` on-device check recommended in §1.2 before treating this as validated.
**RAM headroom:** Plain Chromium kiosk reports in this research (AnotterKiosk's low-end-device tuning, RPi 512MB kiosk discussions) suggest Chromium alone is already a stretch on 512MB without tuning (`low_end_device_mode=1`, disabled compositing/caching), budget to apply the same class of flags, and keep the SPA itself lightweight (avoid heavy client-side frameworks/charting libraries that balloon JS heap) given the shared 512MB ceiling with the kernel, BT stack, and bridge daemon.

### (c) No on-device rendering: Car Thing as pure input satellite, dashboard elsewhere (lowest risk, already validated by prior research)

Keep the original `research.md` §4 to §5 design entirely: the Car Thing runs nothing but the evdev-reading Python daemon talking to the smart-home controller over WebSocket/REST (via USB-CDC-NCM or BT-PAN, §3/§5 of that document); **the React/Angular dashboard runs on the controller host or any other always-on machine/display**, and the Car Thing's touchscreen either shows nothing, a trivial native Qt/EGLFS status screen (confirmed-working rendering path, since this reuses exactly what stock firmware already proves works), or is left dark.

**Pros:** Zero new rendering-stack risk, this is the only option with a directly-confirmed production precedent on this exact hardware (`superbird-debian-kiosk`'s "buttons+dial control a light and recall scenes" feature, `research.md` §4.4) *if* a touch-based UI isn't required at all, or with Qt's already-proven EGLFS path if a native (non-web) status screen is wanted. No Chromium/QtWebEngine GPU uncertainty applies at all, because nothing browser-engine-shaped runs on the device.
**Cons:** Does **not** satisfy the user's stated goal of a React/Angular *UI on the device*, this is explicitly the fallback if (a) or (b) prove infeasible on real hardware, not a way to deliver what was asked. Mention it as the safety net, not the plan.
**RAM headroom:** Trivially fine, a Python asyncio daemon is tens of MB resident (per `research.md` §4.3), leaving nearly all of 512MB free.

### 3.1 Recommendation

Prototype **(b)** first, it's the fastest way to get a real React/Angular SPA rendering on real hardware and get an actual, measured answer to the open GPU-acceleration question (§1.1/§1.2), using components (`yocto-superbird`'s kiosk image, the Python evdev daemon) that are already low-risk per existing research. If `chrome://gpu` shows the kiosk is software-rendered and performance is unacceptable for the intended UI complexity, escalate to **(a)** (QtWebEngine shell) specifically *because* it has the best theoretical chance of inheriting the GPU path that's confirmed working in stock firmware, accepting the Qt/C++ cross-compile cost. Keep **(c)** explicitly as the fallback if both (a) and (b) hit a wall, it's the only option already proven end-to-end on this hardware for the smart-home-control half of the goal, just without an on-device web UI.

## Confidence Assessment

- **High confidence:** Mali-G31 MP2 GPU is the correct GPU for S905D2 (cross-checked, two sources); Panfrost supports Bifrost/G31 GPUs generically and has been run accelerated on the same SoC family (direct hobbyist report); `superbird-debian-kiosk`'s GPU acceleration is explicitly "not working" and the stated reason (missing X11 glue for the vendor Mali/DirectFB stack) is primary-sourced; Yocto's `populate_sdk` SDK-generation mechanism is standard and would work for `yocto-superbird` as a Yocto project; React/Angular build artifacts never need cross-compilation; `yocto-superbird` now ships Chromium-kiosk image variants as first-class, maintained templates (new fact vs. prior research pass); no Electron-on-Car-Thing community report exists.
- **Medium confidence:** QtWebEngine cross-compiles cleanly via Yocto generically (strong generic sourcing, zero device-specific confirmation); whether `yocto-superbird`'s specific kernel/Chromium packaging actually enables GPU acceleration today (plausible given mainline kernel + Panfrost's G31 support, but not directly confirmed); Node.js availability specifically within `yocto-superbird`'s own layer set (generic Yocto node recipes exist, not confirmed wired into this BSP).
- **Could not verify / explicitly flagged unconfirmed:** the full content of the r/carthinghax "yocto-superbird: bluetooth, chrome 147, gpu" announcement post (both Reddit and its pullpush/Unddit mirror failed to fetch in this pass), this likely contains the single most direct answer to "is yocto-superbird's Chromium GPU-accelerated," and should be re-attempted (try the Wayback Machine or a different mirror, or ask in r/carthinghax directly) before finalizing an architecture decision; the claim that *stock* Spotify firmware later moved from Qt+EGLFS to Chromium+Wayland (single secondhand forum comment, contradicts the version-specific primary source in `research.md` §8.8, needs a version-matched teardown to adjudicate, not assumed true or false); any measured FPS/latency numbers for Chromium rendering a dashboard-class or React-SPA-class page on this exact hardware (no source found, qualitative impressions only); actual resident-memory numbers for either Chromium-kiosk or QtWebEngine specifically on this device (extrapolated from other ARM boards/VMs, not measured here).

- https://github.com/bishopdynamics/superbird-debian-kiosk: explicit "GPU acceleration: Not working" status and stated root cause (DirectFB/Mali blob not wired to X11); Chromium kiosk running on stock Amlogic kernel + Debian 11.
- https://github.com/err4o4/spotify-car-thing-reverse-engineering/issues/28: comment claiming newer stock Car Thing OS versions use Chromium+Wayland rather than Qt (unconfirmed, single secondhand source, in tension with `research.md` §8.8).
- https://www.reddit.com/r/carthinghax/comments/1vu4vfy/: yocto-superbird announcement title referencing "chrome 147, gpu..."; full post body not retrievable in this pass (fetch failed; also tried the pullpush/Unddit mirror, also failed).
- https://en.wikipedia.org/wiki/Mali_(processor): SoC-to-GPU mapping table; confirms S905D2 maps to Mali-G31 MP2.
- https://linux-meson.com/hardware.html: canonical Amlogic-mainlining community reference; confirms S905D2 is G12A-family.
- https://forum.manjaro.org/t/panfrost-for-bifrost-gpus-big-improvements/35807: direct hobbyist report of Panfrost running accelerated (`glxinfo` direct rendering: Yes) on an Amlogic S905X3 box with the same Mali-G31 GPU, cross-checking that this GPU family has a working mainline open-source accel path.
- https://docs.mesa3d.org/drivers/panfrost.html: Panfrost driver scope (Midgard/Bifrost Mali GPUs, OpenGL ES + Vulkan via PanVK).
- https://github.com/hexdump0815/linux-mainline-and-mali-amlogic-kernel/blob/master/readme.aml-mali-s905x2-wayland: reference for Amlogic's closed-source vendor Mali kernel-module/blob driver pattern (`mali_kbase.ko`, `libmali.so`) as the alternative to Panfrost on these SoCs, used to explain the stock-firmware GPU access path.
- https://technotes.kynetics.com/2018/yocto-sdk-qt: documented pattern for adding Qt (including QtWebEngine) cross-compilation support to a Yocto standard SDK.
- https://doc.qt.io/qt-6/configure-linux-device.html: Qt's own embedded-Linux device configuration docs; confirms EGLFS backend selection and generic (non-Yocto-specific) cross-compile/sysroot requirements.
- https://docs.yoctoproject.org/sdk-manual/appendix-customizing-standard.html and https://community.nxp.com/t5/i-MX-Processors/How-to-build-the-yocto-SDK/m-p/465026: generic confirmation that `bitbake <image> -c populate_sdk` is standard BitBake/Yocto machinery, available on any valid Yocto project including BSPs that don't document it by name in their own README.
- https://packages.debian.org/nodejs and https://docs.vultr.com/how-to-install-node-js--npm-on-debian-11: confirms `nodejs`/`npm` are ordinary Debian-11/12/13 `apt` packages for `arm64`, supporting the Debian-kiosk-base Node-on-device option.
- https://github.com/Manawyrm/AnotterKiosk/issues/32: concrete low-end-device Chromium tuning flags (`low_end_device_mode`, GPU memory split) specifically for 512MiB-class ARM boards; used as the basis for this document's RAM-headroom cautions.
- https://webengineshackfest.org/2021/slides/kiosk-mode-browser-using-chromium-embedded-framework-cef-by-zakhar-voit.pdf: CEF RAM-usage data point ("approximately 70MB for Google homepage on a 500MB VM"), used as an order-of-magnitude cross-check for Chromium-engine memory footprint discussion.
- `research.md` (this project): prior-pass findings on hardware, firmware landscape, stock-firmware internals (§8), and the Python-based evdev bridge-daemon design (§4.3) reused/extended by this document.
