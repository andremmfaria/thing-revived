# Bluetooth Peripheral Pairing Workflow (chord-triggered, on-screen status)

Research date: 2026-11-16. Status: design only, no code written. Companion implementation ticket should reference this file section-by-section, matching the convention of [`button-knob-clock-design.md`](button-knob-clock-design.md).

This document does **not** re-research BT HID-host feasibility for a keyboard specifically — see [`bt-hid-terminal-feasibility.md`](bt-hid-terminal-feasibility.md) for that (device-acting-as-HID-host mechanism, BCM20703A2 chip, uhid/evdev path). It extends that question to yocto-superbird specifically (§2, the single biggest open item carried over from that doc) and designs the trigger/UI/agent workflow around it.

---

## 1. User's proposed workflow (verbatim recap)

> A new workflow to pair Bluetooth peripherals (starting use case: a keyboard for the terminal, but design it generally for 'peripherals'). Trigger: long-press buttons 1+2 together. While in pairing mode, show a status indicator on the kiosk UI's existing bottom status bar (software UI element, NOT a physical LED — there is no LED on this device) — the indicator should visually read as flashing/alternating red-and-blue while pairing mode is active, as a software animation. After entering pairing mode, the workflow should follow BlueZ's usual pairing/confirmation process for the discovered device.

Three sub-problems this document addresses in turn: (2) whether BlueZ on this specific firmware can even act as an HID host for a keyboard at all (the gating question), (3) detecting the button-1+2 long-press chord from the raw evdev stream, (4) who runs the BlueZ pairing agent and how it handles confirmation with no dedicated input device other than the kiosk's own touchscreen, (5) where the flashing red/blue software indicator should live in the existing UI.

## 2. yocto-superbird BlueZ input/HID-host plugin status — THE blocking question

### 2.1 What was found (read directly from the real BSP checkout on `devel`, `~/workspace/yocto-superbird-build`, read-only, no build triggered)

**`meta-superbird/recipes-connectivity/bluez5/bluez5_%.bbappend`** (the only project-specific bluez customization in this BSP) does exactly two things, neither related to plugins or HID:
- Appends a patch making GATT LE-only (drops BR/EDR ATT PSM-31/SDP, an iOS AMS/ANCS fix).
- `do_install:append()` seds `/etc/bluetooth/main.conf` to set `Class = 0x7c0000`, `Experimental = true`, `KernelExperimental = true`.

It does **not** touch `PACKAGECONFIG`, does not add a systemd unit override, and does not reference HID/input/plugin anywhere. This matches and reconfirms `bt-hid-terminal-feasibility.md` §1's finding — now checked a second, independent way (below), not just re-read.

**`openembedded-core/meta/recipes-connectivity/bluez5/bluez5.inc`** (the base recipe this BSP inherits, unmodified by any bbappend for this purpose) sets the *default* `PACKAGECONFIG` list, which **includes `hid-profiles` and `hog-profiles`**:
```
PACKAGECONFIG ??= "obex-profiles readline ${...systemd...} a2dp-profiles avrcp-profiles
    bap-profiles bass-profiles mcp-profiles ccp-profiles vcp-profiles micp-profiles
    csip-profiles tmap-profiles gmap-profiles hfp-profiles asha-profiles
    network-profiles hid-profiles hog-profiles tools deprecated udev"
PACKAGECONFIG[hid-profiles] = "--enable-hid,--disable-hid"
PACKAGECONFIG[hog-profiles] = "--enable-hog,--disable-hog"
```
`--enable-hid` is BlueZ's upstream `./configure` flag that builds `profiles/input/` — the HID-host profile implementation (BR/EDR HID, device.c/server.c), which is the actual mechanism behind what the stock-firmware research called "the `input` plugin." `--enable-hog` is the BLE-HID-over-GATT equivalent, relevant if a BT keyboard offers HOGP instead of/alongside classic HID. Neither is disabled, filtered, or overridden anywhere in `meta-superbird`.

**The actually-built systemd unit** (read from `build/tmp/sysroots-components/cortexa53/bluez5/usr/lib/systemd/system/bluetooth.service` on a real build output, not just the recipe source) confirms the `ExecStart` line carries **no `--plugin=`/`--noplugin=` restriction**:
```
ExecStart=/usr/libexec/bluetooth/bluetoothd
```
This is the stock oe-core unit, unmodified. This is the decisive fact: stock Spotify firmware's restriction is specifically `bluetoothd --plugin=gap,deviceinfo` on its `ExecStart` line, which is what excludes the HID-host `input` plugin on that firmware. No such flag exists here, at any layer (recipe, bbappend, or built artifact).

### 2.2 Verdict

**Confirmed (not merely re-asserted from the prior doc): yocto-superbird's BlueZ build compiles in HID-host support (`--enable-hid`, `--enable-hog`) and `bluetoothd` is launched with zero plugin restriction, so the HID-host pairing path that was blocked on stock firmware is NOT blocked here.** This closes the single biggest open question flagged in `bt-hid-terminal-feasibility.md` as "left open."

**Confidence: high** that the *build configuration and launch command* enable HID-host support — this was checked from three independent angles (bbappend source, base-recipe `PACKAGECONFIG` defaults, and the actually-built `bluetooth.service` artifact in a real build tree), all three consistent and all primary-source (read directly off the real `devel` checkout, not inferred from documentation).

**Confidence: medium** (not "high") that this translates to a working HID keyboard pairing *in practice* — build-time enablement is not the same as a live, on-device, bonded-keyboard test. No `config.log`/`configure` output was retrievable (BlueZ's `do_configure` work directory had been cleaned, only `temp/` remained), so the exact `./configure` invocation's final flag set wasn't directly captured; only the `PACKAGECONFIG` → configure-flag *mapping* (`--enable-hid`) was confirmed, which is a standard, reliable OE bitbake mechanism, not an inference chain that's likely to be wrong, but it's one link short of literally reading the built binary's compiled-in plugin list.

**Still open (carried forward explicitly, not newly introduced):** nothing in this pass found evidence either way of a live keyboard actually bonding and surfacing a `/dev/input/eventN` node on real yocto-superbird hardware. `bt-hid-terminal-feasibility.md` §5 already flagged "no community precedent" for this exact use case on this exact device, and that remains true. **On-device verification (pair a real BT keyboard, confirm `org.bluez.Input1` appears, confirm a new evdev node emits `EV_KEY`) is still required before implementation, but it is no longer blocked by a known-bad build configuration — it's an empirical check of an otherwise-enabled path, not a "is this even possible" question.**

## 3. Chord + hold-duration detection design (buttons 1+2, in `controller/agent`)

### 3.1 Current state (confirmed by reading `controller/agent/src/main.rs` in full)

No chord or hold-duration logic exists today, anywhere in the codebase. `run_buttons()` only does single-keycode dispatch: broadcast every `EV_KEY` event raw over WS, selectively replay `KEY_M`/`KEY_ENTER` via uinput, and a single hardcoded `KEY_ESC`-press-value-1 branch for the hard-recovery restart (`button-knob-clock-design.md` §7). There is no per-key timestamp tracking, no multi-key state, and no hold/duration threshold anywhere in `run_buttons()`'s event loop — it is a pure stateless raw-event relay plus two special-cased single-key branches. Confirmed keycodes on `/dev/input/event0` (already grabbed exclusively here, see §3.3): `KEY_ESC=1`, `KEY_1=2`, `KEY_2=3`, `KEY_3=4`, `KEY_4=5`, `KEY_ENTER=28`, `KEY_M=50`.

### 3.2 Is there a standard/idiomatic Linux mechanism for this, or is it application-level?

**Finding: application-level only; there is no kernel or libinput primitive for "N keys held together."** Two independent primary-source confirmations:

- **python-evdev maintainer's own answer** to exactly this question ("what's the proper way to detect long press on a key"): *"There's nothing builtin, I'm afraid — python-evdev just exposes what evdev provides."* The maintainer's own worked example is precisely the pattern this section proposes: record a press timestamp per key-code into a map on `value==1`, delete the entry on `value==0`, and poll/compare `now - ts` against a threshold, yielding once per hold rather than repeatedly. (github.com/gvalkov/python-evdev, issue #70, confirmed answer from the repo owner.) The kernel itself does expose a single-key repeat/hold signal (`value==2`, "key is being held," i.e. standard autorepeat) but nothing for duration thresholds or multi-key combinations — that is unambiguously userspace's job.
- **systemd-logind's own power-key long-press handling** — the closest "idiomatic OS-level" prior art for "long-press a key to trigger a different action than a short press" — is implemented exactly this way: logind starts a timer on key-down and distinguishes short-vs-long press by whether the timer fired before release, entirely in logind's own application code against the same evdev-style event stream, not via any dedicated kernel long-press primitive. (Confirmed both from `logind.conf(5)`'s documented `HandlePowerKeyLongPress=` behavior, and from a live systemd GitHub issue, #38534, describing exactly the press/timer/release state machine logind maintains internally and a bug in that state tracking — i.e., this is genuinely a hand-rolled timer+state-map mechanism in widely-deployed, security-sensitive system code, not a toy pattern.)

**Confidence: high.** Two independent, primary-source confirmations (library maintainer statement + systemd's own documented/observed behavior) agree: timestamp-tracking in application code is the established approach, not a one-off hack.

### 3.3 Proposed design, sited in `run_buttons()`

Chord detection sits in the same function that already owns the grabbed `/dev/input/event0` fd and the per-event `match` on `EventType::KEY` — this is additive to the existing loop, not a parallel mechanism, consistent with how `KEY_ESC`'s hard-recovery branch was added in §7 of `button-knob-clock-design.md`.

1. **New per-button press-timestamp state**, local to `run_buttons()` (no need for a shared `Arc<Mutex<_>>` — this state is read and written only inside the single-threaded button-read loop, same scope the existing code already runs in): a small map or two `Option<Instant>` fields, `key1_down_at: Option<Instant>`, `key2_down_at: Option<Instant>`, set on `code == KEY_1 && value == 1` / `code == KEY_2 && value == 1` respectively, cleared to `None` on the corresponding `value == 0` (release).
2. **Chord-armed check**, evaluated on every event (not just on button 1/2 events, so a hold that crosses the threshold without a *new* event firing is still caught — see the polling note below): if both `key1_down_at` and `key2_down_at` are `Some`, AND they were set within some small window of each other (e.g. 500ms — "pressed together," not "both happen to be down because of unrelated drift"), AND `now - max(key1_down_at, key2_down_at) >= HOLD_THRESHOLD_MS` (proposed: 1500–2000ms, long enough to not trigger on an accidental simultaneous tap, short enough not to feel broken), fire the "enter pairing mode" action exactly once per qualifying hold (track a `chord_fired: bool` flag, reset when either key releases, mirroring the python-evdev example's "delete from state map so it only triggers once" pattern from §3.2).
3. **Polling concern:** `device.fetch_events()` blocks until the kernel has an event to deliver — it will **not** wake up on its own purely because 2000ms has elapsed with no new key activity, so a chord held perfectly still (no repeat events) might not get its threshold check re-evaluated promptly. Two options, prefer the first: (a) rely on hardware autorepeat — `gpio-keys-polled` typically does emit periodic `value==2` "repeat" events while a key is held (same mechanism already used for the single-key hold detection in §3.2's examples), which gives the loop a wakeup to re-check the threshold without any separate timer; confirm this empirically on this exact driver before committing to it as the sole mechanism. (b) if repeat events prove absent or too infrequent, add a short (e.g. 100ms) `read_timeout`-style poll instead of (or alongside) blocking `fetch_events()`, following the second python-evdev example in §3.2 (`select()` with a timeout, check all held-key durations on every timeout tick regardless of whether a new event arrived). This is a small, well-precedented pattern, not a new category of complexity.
4. **Action on chord-threshold-reached:** call a new function, e.g. `enter_pairing_mode()`, which (a) broadcasts a new WS message type over the existing `ws://0.0.0.0:8765` connection so the frontend can show the indicator (§5), and (b) either calls into BlueZ directly from this same process (see §4's placement discussion) or shells out / signals whichever process owns the D-Bus agent.
5. **Generalization beyond buttons 1+2:** nothing above is specific to KEY_1/KEY_2 — the same two-key-timestamp-plus-threshold pattern generalizes to any chord of two (or more, with a small `Vec`/map instead of two named fields) keys on this device, which matches the user's own framing of "design it generally for peripherals," i.e. the *trigger* mechanism is reusable even though the *initial* binding is buttons 1+2.

### Why not elsewhere
`terminal/agent` (port 8766) has no evdev access at all (confirmed in `button-knob-clock-design.md` §0) and would need a new WS round-trip from `controller/agent` just to learn about a chord it can't detect itself — strictly worse than detecting it where the raw events already live. `app.js` could theoretically reconstruct the chord from the two independent `'button'` messages it already receives, but that pushes a timing-sensitive, security/adjacent-to-system-control decision (entering BT pairing mode) into the browser tab, which is exactly the kind of fragile, UI-process-dependent design `button-knob-clock-design.md` §7 explicitly rejected for the ESC hard-recovery case ("a design that routes this through app.js's JS event loop... is exactly the kind of path that can itself be wedged"). The same reasoning applies here: `controller/agent` is the right place.

## 4. BlueZ pairing-agent integration design

### 4.1 BlueZ's real agent API (primary source)

BlueZ's agent interface (`org.bluez.Agent1`, registered via `org.bluez.AgentManager1.RegisterAgent(object, capability)` + `RequestDefaultAgent(object)`) exposes these methods a custom agent implements (per `doc/org.bluez.Agent.rst`, the current upstream doc, successor to the older `doc/agent-api.txt` referenced in the task — both describe the same interface, the `.rst` is BlueZ's present-day format):

- `RequestPinCode(device) -> string`, `DisplayPinCode(device, pincode)` — legacy PIN-entry pairing.
- `RequestPasskey(device) -> uint32`, `DisplayPasskey(device, passkey, entered)` — 6-digit passkey entry/display.
- **`RequestConfirmation(device, passkey)` — the one most relevant to a BT keyboard:** called when BlueZ needs the *local* side to confirm a passkey shown on the remote device (or, for Secure Simple Pairing/LE Secure Connections numeric comparison, confirm the passkey the agent itself would display matches what's on the remote). Reply with an empty response to accept, or `org.bluez.Error.Rejected`/`Error.Canceled` to reject.
- `RequestAuthorization(device)` / `AuthorizeService(device, uuid)` — authorize a bonded-but-unconfirmed device or a specific profile/service.
- `Cancel()` — the daemon tells the agent to abandon an in-flight request (e.g. remote side cancelled).

**Which method actually fires for a BT keyboard depends on the keyboard's own I/O capability and the negotiated pairing model, not something this project's agent controls unilaterally.** `bluez-peripheral`'s own pairing-security matrix (secondary but directly on-point source, cross-referenced against BlueZ's own IO-capability-driven model which the matrix summarizes correctly) shows: a keyboard-only peripheral (`KeyboardOnly` capability) pairing with an agent that has `KeyboardDisplay` or `DisplayYesNo` capability resolves to **Passkey Entry** (the keyboard's user types a passkey this device displays) — **not** silent "Just Works." Only if the agent registers with `NoInputNoOutput` capability does the whole exchange collapse to Just Works with no user interaction on either side (and a Just Works pairing may lack MITM protection, which is BlueZ's own documented tradeoff, not this project's choice to make lightly).

**Design implication:** since this device has a touchscreen capable of displaying a passkey and (for yes/no confirmation) capable of accepting a tap, the agent should register with **`KeyboardDisplay` or `DisplayYesNo` capability**, not `NoInputNoOutput` — this gets the MITM-protected flow where the kiosk's own screen shows a 6-digit code (`DisplayPasskey`) or a yes/no prompt (`RequestConfirmation`) and the *physical BT keyboard's own keystrokes* (typed into itself, not into this device) are what the far side uses to enter/confirm the code, which is exactly the normal flow for pairing a classic BT keyboard to anything (a PC, a phone) — this project does not need to invent a different flow, it needs to implement the UI side of a well-established one.

### 4.2 Where does the agent run — confirm or challenge the `controller/agent` placement

**Confirmed, with one caveat.** `controller/agent` is the only component that both (a) owns the evdev/chord-detection trigger (§3) and (b) is a long-running, always-on native process capable of holding a D-Bus connection — `terminal/agent` has neither evdev nor any existing D-Bus use, and `terminal/frontend/app.js` is sandboxed browser JS with no D-Bus access at all (Chromium's kiosk renderer cannot open a system-bus connection directly; it would need some native bridge regardless). So the same process that detects the chord registering the agent and driving the whole pairing D-Bus flow is the natural, lowest-friction placement, and avoids yet another cross-process round-trip for a latency/race-sensitive operation (BlueZ's agent methods are synchronous D-Bus calls with their own timeouts — adding a WS hop to a second Rust process in between before replying would be strictly worse).

**Caveat/challenge worth flagging, not silently resolved:** `controller/agent` today has no D-Bus dependency at all (pure `evdev` + raw `TcpListener`/`tungstenite` WebSocket server, no `dbus`/`zbus` crate). Adding a full D-Bus agent implementation is a materially larger dependency footprint than anything currently in that binary (BlueZ's agent protocol requires implementing an actual D-Bus object with multiple exported methods, not a client-side call — the `zbus` crate's `#[interface]` macro is the standard modern Rust way to do this, replacing the deprecated `dbus-rs`). This is a legitimate scope increase to that binary's responsibilities (today: "evdev bridge," proposed: "evdev bridge *and* BlueZ pairing-agent host"), and is worth the user/Thinker explicitly signing off on rather than treating as a foregone conclusion — the alternative (a small *separate* sidecar process, spawned by `controller/agent` only while pairing mode is active, communicating pairing-flow state back over the same existing WS broadcast mechanism) would keep the always-on binary lean and only pay the D-Bus/zbus dependency cost in a short-lived child process, at the cost of one more moving part and IPC hop. **This document recommends the single-binary approach (simpler, fewer processes, pairing is infrequent so the dependency footprint cost is paid once at compile time not at runtime) but flags the alternative as a real, reasonable tradeoff, not a strawman.**

### 4.3 Headless/kiosk-touchscreen confirmation flow, concretely

1. On chord-threshold fire (§3.3 step 4), `controller/agent`:
   a. Opens (or already holds) a D-Bus system-bus connection.
   b. Calls `org.bluez.Adapter1.SetDiscoverable(true)` / sets `DiscoverableTimeout` and `Pairable`/`PairableTimeout` (see §5 below for the actual timeout values) on the relevant adapter object (`/org/bluez/hci0` or equivalent).
   c. Starts `StartDiscovery()` to find nearby devices (general "peripherals," not keyboard-specific — matches the user's "design it generally" framing; the frontend/UI can filter by a device-class hint, e.g. HID major class, for a "keyboard" picker, without that filtering being a BlueZ-level restriction).
   d. Registers an `org.bluez.Agent1` object (capability `KeyboardDisplay` or `DisplayYesNo`, per §4.1) and calls `RequestDefaultAgent`.
   e. Broadcasts the "entering pairing mode" WS message (drives §5's indicator) immediately, independent of discovery results.
2. When a candidate device appears (`InterfacesAdded` signal on a new `/org/bluez/hci0/dev_XX_XX...` object, or a discovered-device list polled via `GetManagedObjects`), surface it to the frontend over the existing WS channel as a new message type (e.g. `{"type":"bt_device_found","address":"..","name":"..","class":".."}`), letting the kiosk UI show a "pair with this?" prompt — this is new UI surface, not designed in pixel detail here, just the data path.
3. On user selecting a device (touchscreen tap), `app.js` sends a `{"type":"bt_pair","address":".."}` control message back over the existing WS connection; `controller/agent` calls `Device1.Pair()` on that object path.
4. BlueZ's agent callbacks (`DisplayPasskey`/`RequestConfirmation`, whichever the negotiated IO-capability pairing produces per §4.1) fire on the registered agent object; the agent implementation relays the passkey/confirmation request to the frontend over WS (new message types, e.g. `{"type":"bt_confirm","passkey":"123456"}`), the frontend shows it on the touchscreen, the user taps accept/reject, `app.js` sends the result back, and the agent's D-Bus method handler replies to BlueZ accordingly (empty success reply, or `org.bluez.Error.Rejected`). This is the same request/response-over-an-existing-WS-channel pattern `terminal/agent`'s `control`/`respawn` messages already establish (`button-knob-clock-design.md` §1/§8) — not a new category of plumbing, an application of an already-proven one.
5. On success, call `Device1.Connect()` / rely on BlueZ's own auto-connect-on-trust behavior, and `Adapter1.Pairable`/`Discoverable` should be turned back off (or simply allowed to hit their own timeout, §5) to leave the adapter in its normal resting state; broadcast "pairing mode ended" to clear the indicator.

### 4.4 Real-world precedent for this shape of design

- **AGL (Automotive Grade Linux) Bluetooth Settings module** (a GSoC 2026 project building a Flutter-based in-vehicle homescreen's Bluetooth settings on top of BlueZ): documents registering a custom `org.bluez.Agent1` implementation over D-Bus with an explicit "Pairing Agent Contract" table covering `RequestPinCode`/`RequestPasskey`/`DisplayPinCode`/`DisplayPasskey`/`RequestConfirmation`/`RequestAuthorization`/`AuthorizeService`/`Cancel`/`Release`, using `KeyboardDisplay` capability, and states explicitly that "pairing prompts are used only for real BlueZ requests" — i.e. the UI renders whatever the agent callback actually receives, not a simulated flow. This is a materially similar deployment shape (kiosk-style vehicle touchscreen UI, no physical keyboard on the host device, BlueZ-driven pairing) to this project's own design, and corroborates the §4.1–4.3 flow as a proven, not invented, pattern. (jaydon2020.github.io/agl-bluetooth-integration-gsoc26, dated 2026, actively-revised project documentation, not a finished/shipped product postmortem — flag as a design doc for an in-progress project, not a battle-tested shipped reference, but still real independent validation of the same agent-contract shape.)
- **`bluez_peripheral`'s `YesNoAgent`/`TestAgent`** (a maintained Python BlueZ-agent library, `bluez-peripheral.readthedocs.io`) independently confirms the same agent-registration pattern (`register(bus, default=True)`, capability-driven behavior) and explicitly documents the IO-capability pairing-model matrix cited in §4.1 — useful as a second, independent, code-level confirmation of the mechanics (not a kiosk-specific precedent itself, since `bluez_peripheral` is a general-purpose library, not a shipped device).
- **Not found:** a precedent that is *both* (a) a shipped/widely-used consumer kiosk device and (b) specifically pairing an HID peripheral (as opposed to a phone, or a PAN gateway) via an on-screen agent. The AGL project above is the closest match found and is itself still in development. This should be stated as "pattern proven in principle and in at least one comparable in-progress automotive project, not confirmed in a shipped consumer product," rather than overstated as "this exact thing has shipped before."

## 5. UI indicator design — where does the flashing red/blue pairing-mode indicator live

### 5.1 Candidates inspected

- **`terminal/frontend`'s existing bottom `.status-bar`** (confirmed by reading `terminal/frontend/index.html`/`style.css`): a flex row containing `AGENT: <status>` / `BRIDGE: <status>` dot-pairs and a `session: --` text field, plus (per `button-knob-clock-design.md` §4) a `.clock-widget` anchored right via `margin-left: auto`. This bar already establishes a reusable `.status-dot` / `.status-dot.ok` / `.status-dot.stale` CSS convention (colors: red default, green `ok`, amber `stale`) that a new state could extend.
- **`prototype/dashboard`'s Bluetooth-adapter-up/down display** (confirmed present, at the time of this research, via file listing — `prototype/dashboard/agent/src/main.rs` and `prototype/dashboard/frontend`; this is the `hciconfig`-based adapter-state surface the task brief names). This was a **separate prototype app** from the terminal — a different binary (`noc-agent`), different frontend, different purpose (network/operations-style status dashboard, not the interactive terminal kiosk). `prototype/dashboard` has since been removed from the repo entirely (never deployed, no replacement); this section's comparison is retained as the historical reasoning for why the indicator landed in `terminal/frontend` instead.

### 5.2 Recommendation: `terminal/frontend`'s existing status bar, not `prototype/dashboard`

**Reasoning:**
- The trigger (buttons 1+2 long-press, §3) fires from `controller/agent`, which already has a live WebSocket fan-out to **whichever frontend is currently the kiosk's active, focused app** — and per the project's own architecture, that is `terminal/frontend` (it already consumes this exact bridge's `'button'`/`'knob'` messages; `prototype/dashboard` was described in the task brief as a separate prototype, not the thing actually running full-time as "the kiosk UI"). Putting the indicator in `prototype/dashboard` would have meant a user had to switch to a different app entirely to see feedback for an action they triggered via physical buttons while using the terminal — a confusing cross-app jump for state that's fundamentally about "what is this device doing right now," which belongs wherever the user's attention already is.
- `terminal/frontend`'s status bar is explicitly, by design, the place for "is some always-relevant background subsystem alive/healthy" indicators (`AGENT`/`BRIDGE`/clock), which is precisely the category "are we currently in BT pairing mode" belongs to — it's not specific to any one terminal session (unlike the tab/session-switch UI), it's device-wide state, exactly like the existing dots.
- A dedicated overlay/toast was considered and is not recommended as the primary location: pairing mode is not a one-shot transient notification (a toast's natural use case), it is a *sustained mode* lasting up to the discoverable/pairable timeout (§5.3) — the existing always-visible status-bar-dot pattern (which already models exactly this: a persistent state indicator, not a one-off alert) fits better than a toast that would need its own auto-dismiss/re-show logic duplicating what the status bar already does for free. A transient toast *in addition to* the status-bar indicator, purely to call initial attention to pairing mode having started, is a reasonable cosmetic addition but not a substitute for the persistent indicator, and is not designed further here (same "optional, not required, skip unless requested" treatment other cosmetic additions got in `button-knob-clock-design.md`).

### 5.3 Concrete design, reusing the established `.status-dot` pattern

- New `#bt-pairing-dot` / `#bt-pairing-text` pair, same markup shape as `agent-dot`/`bridge-dot` in `terminal/frontend/index.html`'s `.status-bar`, shown only while pairing mode is active (`display: none` otherwise — unlike `AGENT`/`BRIDGE` which are always shown, this one should not permanently occupy status-bar real estate for a rare, short-lived mode).
- **Software flashing red/blue animation**, not a static color — a CSS `@keyframes` alternating `background`/`box-shadow` between the existing `--red` and a new `--blue` CSS custom property (the status bar's existing palette already defines `--red`/`--green`/`--amber`-equivalent via the `.status-dot` base + `.ok`/`.stale` modifiers per `style.css`; add `--blue` alongside them), e.g.:
  ```css
  @keyframes bt-pairing-flash {
    0%, 49%   { background: var(--red);  box-shadow: 0 0 6px var(--red); }
    50%, 100% { background: var(--blue); box-shadow: 0 0 6px var(--blue); }
  }
  .status-dot.pairing { animation: bt-pairing-flash 1s step-end infinite; }
  ```
  This is a **pure CSS/software animation on an existing DOM element class** — explicitly not any physical LED or GPIO output, consistent with the hardware fact that this device has no LED of any kind. `step-end` (vs. a smooth transition) is recommended to read as a distinct two-state "flash" rather than a smooth color fade, matching the user's "flashing/alternating" wording more literally than a CSS `transition` would.
- Driven by the same `connectBridge()`/`onmessage` pattern already used for `'button'`/`'knob'` messages (`app.js`): a new message type from `controller/agent`, e.g. `{"type":"bt_pairing_mode","active":true}` / `{"active":false}`, toggles `.pairing` class + `display` on the new dot, and sets `#bt-pairing-text` to `"BT PAIRING..."` or similar — zero new WS connection, same existing bridge channel the button chord was detected on in the first place.
- **Discoverable/pairable timeout — sane default to drive how long this indicator stays flashing:** BlueZ's own `Adapter1.DiscoverableTimeout` documentation (`doc/org.bluez.Adapter.rst`, cross-checked against `bluez.readthedocs.io`'s adapter-API page and an independent 5.49-era mirror on `kernel.googlesource.com`, all three consistent) states the property's **own built-in default is 180 seconds (3 minutes)**, and `PairableTimeout`'s documented default is **0 (disabled/forever)** — BlueZ does not auto-disable pairability on its own unless a caller sets a non-zero value. **Recommendation: explicitly set both `DiscoverableTimeout` and `PairableTimeout` to the same bounded value (120–180s is BlueZ's own documented convention, not an invented number) when entering pairing mode**, rather than relying on `Pairable`'s unbounded default — this both matches common vendor/BlueZ convention and gives the UI indicator (and the underlying adapter state) a deterministic, finite "pairing mode" window that self-closes if the user walks away without completing pairing, instead of leaving the adapter silently pairable-forever. On adapter-driven timeout expiry, BlueZ flips `Discoverable` back to `false` itself (per the same doc — "the system will set this value back to false after the timer expired") and emits a `PropertiesChanged` signal the agent-hosting process should listen for, to broadcast the matching `{"active":false}` WS message and clear the indicator even when the user never explicitly cancelled.

## 6. Open questions, ranked by how blocking each is

1. **(Was the #1 blocker, now downgraded to "verify, don't redesign around a hypothetical failure"): live on-device confirmation that a real BT keyboard actually bonds and surfaces a usable evdev node on yocto-superbird.** §2 confirmed the *build* enables HID-host support and removes the known stock-firmware blocker, but no live pairing test exists yet on this exact BSP/kernel/chip combination. This is now the top remaining risk precisely because it's the one thing in this whole design that can't be resolved by reading more source — it needs a flashed device, a real BT keyboard, and `bluetoothctl`/`evtest`.
2. **D-Bus dependency footprint in `controller/agent` (§4.2).** Not a feasibility blocker, but an architecture decision explicitly flagged as not yet signed off: single-binary-grows-a-D-Bus-agent vs. a short-lived sidecar process. Should be decided before implementation starts, since it changes the shape of nearly every other piece of §3/§4.
3. **Chord-detection wakeup mechanism (§3.3 step 3): does `gpio-keys-polled` on this device actually emit periodic autorepeat (`value==2`) events while buttons 1/2 are held, frequently enough to re-check the hold threshold without a separate poll/timer?** Unconfirmed either way — plausible given the generic Linux input-core autorepeat mechanism, but not verified against this specific driver instance's autorepeat settings (`EVIOCGREP`/`input_dev->rep[]`). Low effort to check live (`evtest` while holding a button), low architectural risk either way (the timeout fallback in step 3(b) is a simple, well-precedented substitute if autorepeat proves absent or too coarse), hence ranked below the two items above rather than at the top.
4. **Exact chord-window and hold-duration constants (§3.3: proposed 500ms simultaneity window, 1500–2000ms hold threshold)** are reasonable engineering judgment, not sourced from any measured user-testing data for this device — worth a quick empirical "does this feel right" pass during implementation, low risk of being wrong by an order of magnitude, not blocking design work.
5. **Device-class/UI filtering for "peripherals" discovery (§4.3 step 2c)** — generalizing beyond "keyboard" to a broader peripheral picker is a product/UI-design decision (what to show, how to filter/sort discovered devices) explicitly out of scope for this research doc to decide; flagged, not designed.
6. **Toast/initial-attention-grab addition alongside the persistent status-bar indicator (§5.2)** — optional cosmetic polish, not required for a functional MVP, consistent with how other optional cosmetic additions were treated in `button-knob-clock-design.md`.
