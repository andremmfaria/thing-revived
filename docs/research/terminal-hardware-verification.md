# Terminal: Real-Hardware Verification History

Historical record of the terminal feature's development and real-hardware verification, moved out of `terminal.md` (which now covers only the current design). See [`terminal.md`](../terminal.md) for the current architecture, wire protocol, and known limitations.

## Original design and implementation

The terminal is a standalone deliverable: a terminal emulator rendered by the Chromium kiosk, backed by a real PTY on the device, reachable from a Bluetooth-paired keyboard. Motivated by the feasibility research in [`bt-hid-terminal-feasibility.md`](bt-hid-terminal-feasibility.md), which this feature implements the "implication for a terminal UI" section of.

## What was verified on real hardware during the first deployment

Deployed and exercised for real against the physical unit, serial `8559R486QR1S`, on stock DeskThing-modified firmware (not yet `yocto-superbird`).

- **Deployment**: pushed the `armv7-unknown-linux-gnueabihf` / `+crt-static` binary, `terminal-agent-config.json`, the frontend files, and the supervisord conf; `supervisorctl status` showed `thing-revived-terminal: RUNNING` alongside the pre-existing `thing-revived-bridge` and `thing-revived-noc-agent` units with no manual process management.
- **Two real bugs found and fixed by this deployment, not caught by earlier desktop-only testing:**
  1. `Session::new` panicked the entire process (not just the one failing session) when a configured session's command couldn't spawn. On real hardware the shipped example config's `ssh-devel` entry failed exactly as `bt-hid-terminal-feasibility.md` predicted (no ssh client on this firmware), which crash-looped the whole agent under supervisord's `autorestart`. Fixed: `Session::new` now returns `Result` instead of panicking, `main()` logs and skips a failed session instead of aborting, and `dispatch()` now looks up sessions by their own `index` field instead of raw vector position (needed once a failed session can be absent from that vector).
  2. `control`/`respawn` correctly spawned a new child process and PTY, but the per-session output-reader thread exits permanently on its old child's EOF by design, and nothing restarted it for the new child — so a respawned session ran but went silently deaf, no output ever reached the frontend again. Fixed: `respawn`'s handler now spawns a fresh `pump_session_output` thread alongside the new child.
- **Protocol round trip, for real, against the actual on-device shell**: a raw WebSocket test client got a real handshake, the `session_list` message, and `echo HELLO_FROM_REAL_DEVICE_TEST` typed over `input` round-tripping back through the PTY's actual `stdout` as an `output` message. Re-ran the same test immediately after a `control`/`respawn` message to confirm fix #2 above: output kept flowing on the new child, not just the original one.
- **Rendering, for real, on the actual on-device Chromium 69** (**Correction 2026-11-22: the owner confirms the device runs Chromium 68; 69 was recorded here in error**): forwarded the remote-debugging port, navigated the kiosk's live page to the terminal's `file://` path, and screenshotted it: the `local-shell` session tab, the status bar's `AGENT: LIVE` / `BRIDGE: LIVE` indicators (confirming both the new terminal WebSocket and the pre-existing bridge daemon's WebSocket connect successfully), and a correct render of typed input and real shell output were all confirmed visually.
- **Keyboard input path, verified by proxy, not by a real BT keyboard**: no BT keyboard was paired at this point (blocked by the firmware gap below). Instead, CDP's `Input.dispatchKeyEvent` was used to inject real `keydown`/`keyup` DOM events at the browser level after focusing `#screen`, the same event type a real paired keyboard would generate. This proved the page's `keydown` handler → WebSocket `input` message → PTY write path works end to end on real Chromium 69, but was a proxy for, not a replacement for, confirming an actual BT keyboard surfaces as an evdev node on this hardware.

## Known limitations found on this early real-hardware session (resolved since)

- **The unit was still on stock DeskThing-modified firmware, not `yocto-superbird`, at this point.** Per `bt-hid-terminal-feasibility.md`, stock firmware's `bluetoothd` explicitly whitelisted `--plugin=gap,deviceinfo`, excluding the `input` (HID-host) plugin, so a real BT keyboard could not be paired as an input peripheral on that firmware. Resolved by the `yocto-superbird` reflash (see [`../yocto-build-and-flash.md`](../yocto-build-and-flash.md)), which enabled the kernel's `CONFIG_UHID` and the `bluetoothd` `input` plugin: real BT-keyboard pairing is now directly confirmed working on the physical unit, paired and typing into live terminal sessions.
- SSH client presence on stock firmware: confirmed absent (`ssh-devel` session's `ENOENT` on spawn), consistent with `bash-availability.md`/`bt-hid-terminal-feasibility.md`'s prediction. The agent degraded gracefully instead of crashing, per fix #1 above. Resolved on `yocto-superbird`: `bash`, `openssh-ssh`, and `openssh-keygen` are added to the image (see `yocto-build-decisions.md`).
- Real button/knob scancode-to-action mapping: resolved, see [`button-knob-clock-design.md`](button-knob-clock-design.md).

## Language rewrite history

`daemon/` originally shipped as a Python 3.7 stdlib script (`terminal-agent.py`, hand-rolling a minimal RFC 6455 WebSocket server because the stdlib has none), specifically to avoid paying for a second cross-compile target beyond `controller/`'s own. It was later rewritten in Rust and the Python source deleted; no Python remains anywhere in this repo. Reasoning for the rewrite:

- `controller/` already paid the cross-compile cost once; paying it a second time for this component was no longer a reason to avoid Rust, and it removed the hand-rolled, materially less battle-tested WebSocket implementation the Python version carried as an explicit, acknowledged tradeoff.
- **WebSocket server:** `tungstenite`, the same crate `controller/src/main.rs` already depends on — specifically the sync variant (`tungstenite::accept` + one OS thread per client), not an async `tokio-tungstenite` runtime, matching `controller/`'s own sync/threaded style.
- **PTY handling:** `libc::openpty` plus `std::process::Command` with `CommandExt::pre_exec` for `setsid()` followed by `ioctl(slave_fd, TIOCSCTTY)`, mirroring Python's `pty.openpty()` + `subprocess.Popen(..., preexec_fn=os.setsid)` plus one additional fix the Python version never needed to make explicit. `setsid()` alone makes the child a session leader with no controlling terminal; since the slave fd here is `dup()`'d rather than freshly `open()`'d, the kernel's normal "open() of an unowned tty by a ctty-less session leader" auto-attach path never fires either. Without the `TIOCSCTTY` ioctl, a `resize` WS message's `ioctl(master_fd, TIOCSWINSZ)` call produced zero visible effect — no `SIGWINCH` ever reached the child. This broke two things before the fix: `ssh` never forwarded the real window size to the remote process, and `bash` never redrew its prompt on resize. `nix` was considered but checking `controller/src/main.rs` directly showed it is only a transitive dependency of `evdev`, never called by `controller/`'s own code — no actual direct-dependency precedent to match, so `libc` was used directly instead.
- An earlier version of this agent/frontend pair sent a static `80`/`24` size on every connect, which is why a remote curses process never filled the kiosk's real screen width and a freshly-switched-to shell tab never redrew its prompt either; this was fixed by having `FitAddon` compute real `cols`/`rows` live from the container's actual pixel size on every connect/resize/tab-switch.

## Bridge daemon extension point: original (unimplemented) design, now superseded

When this feature was first designed, the button/knob-to-session-action translation was left unimplemented in `controller/`, with the original reasoning: `hardware-interaction.md`'s own "Open item carried over" stated the exact scancode-to-physical-button mapping was still unconfirmed, pending a live capture on real hardware. Teaching `controller/` to translate raw codes into logical `session_action`/`scroll` messages before that capture happened would have meant hardcoding a guessed mapping into the one process every other feature also depends on, with a real risk of breaking its currently-working behavior on a guess. The frontend instead consumed `controller/`'s raw `{"type":"button",...}` / `{"type":"knob",...}` messages directly, doing the code-to-action translation client-side with a placeholder table.

This extension point has since been implemented for real: the `EVIOCGRAB`+`uinput` mechanism, the confirmed `BUTTON_SESSION_MAP`, and the full button/knob design are documented in [`button-knob-clock-design.md`](button-knob-clock-design.md), which is the current, authoritative source for this mechanism — not this historical note.
