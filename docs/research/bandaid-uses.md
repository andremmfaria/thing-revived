# Bandaid partition: upstream intent and uses for thing-revived

Research date 2026-11-27. Read only: nothing built, flashed or run on a device. Upstream BSP checkout read: `/home/andremmfaria/workspace/yocto-superbird-build-2` (paths below are relative to it unless prefixed `tr:` for the thing-revived repo). Web sources were fetched today and are listed at the end. Status key: V verified in a file or page fetched today, I inferred (reasoning stated), U unverified.

## Summary

Bandaid is upstream's "independently updatable vendor payload" partition: a small ext4 holding the application daemon and its built-in webapps, bind-mounted at `/opt/<vendor>`, so the app can be hot-updated without writing a root slot. It is designed as disposable and rebuildable (fsck reformats it, rollback wipes it, a factory copy in the root reseeds it), it is rewritten by every full flash, and it is never touched by OTA. That makes it a poor home for anything that must survive (secrets, identity, logs) and a good home for exactly one thing this project needs: a writable, size-capped `/opt` for Entware, preseeded at build time. Recommendation: use it for Entware and keep 192 MiB, or, if Entware goes to `/var`, shrink it to a few tens of MiB rather than fork the wks to remove it.

## Upstream intent (with citations)

- Purpose, layout and update model. `meta-bridgething/README.md:29` describes `bandaid.ext4` as "the daemon binary plus hub and stock for the bandaid partition; flashed initially, OTA'd as `applyUpdate { kind: daemon | builtin-webapp }`" (V). The example layer README says daemon-only or webapp-only updates "skip the slot flip" and the bandaid bind-mount "is the surface": a writer streams a new binary into `/var/lib/bandaid/<vendor>` and atomic-rotates `.current`/`.previous` (`examples/meta-superbird-kiosk-example/README.md`, section OTA, and the iteration loop that says the write "survives a slot flip") (V). The GPT layout is `env + boot_a + root_a + boot_b + root_b + bandaid + data` (https://github.com/JoeyEamigh/yocto-superbird README) (V).
- Independent of image OTA. The full and delta `sw-description` write only `boot_a`, `root_a`, `boot_b`, `root_b` by partlabel (`meta-superbird/recipes-core/superbird-bsp-update/files/full/sw-description:18,24,38,44`; delta lines 19 to 60) (V). So no swupdate image ever updates bandaid, and no delta mechanism for bandaid exists in the BSP (V by absence in those files). Updating it is the daemon's job: bridgething's OTA kinds are `image`, `daemon`, `builtinWebapp`, `installedWebapp`, `wakewordModel` (https://bridgething.com/docs/system/) and Nocturne's are `image`, `daemon`, `builtin-webapp`, `bandaid` (https://github.com/usenocturne/nocturne README) (V). Nocturne also builds a standalone replaceable `bandaid.ext4` that "can directly replace the same-named entry in a base flashthing ZIP" (https://github.com/usenocturne/nocturne/blob/main/image/README.md) (V).
- Reconciling a stale bandaid after an image OTA. bridgething ships `bridgething-adopt-daemon`, which keeps whichever of the bandaid and image-baked daemon or webapp is newer, per component (`meta-bridgething/recipes-core/bridgething-daemon/files/bridgething-adopt-daemon:24-65`, tests in `scripts/test-adopt-daemon`) (V). Nocturne's `nocturne-floor-sync` compares the baked floor version to `.floor-version` on bandaid and promotes atomically (https://docsearch.algolia.com/mcp/docs/repo/usenocturne/nocturne, derived from its meta-nocturne README; the raw README row confirms "re-seeds the bandaid floor from rootfs on OS upgrade") (V). The `opt-overlay` seed is seed-once: it copies `/usr/lib/<vendor>` only when `/var/lib/bandaid/<vendor>` is missing (`meta-superbird/recipes-core/opt-overlay/files/opt-overlay-bind:20-28`) (V), which is why the floor-sync layer exists.
- Disposable by design. `superbird-fsck.sh:10` sets bandaid `UNREPAIRABLE=format` (data is `leave`), and line 79 reformats it after failed repair; the 0.2.4 release note reads "journal the bandaid and automatically repair fs corruption" (`releases/0.2.4.md:5`) (V). `bridgething-rollback` on a failing daemon promotes `.previous`, and if none exists it does `rm -rf /var/lib/bandaid/bridgething` and reboots "to factory" (`meta-bridgething/.../bridgething-rollback:2,23`) (V).
- Factory fallback when bandaid does not mount. fstab is `PARTLABEL=bandaid /var/lib/bandaid ext4 rw,noatime,sync,nofail` (`meta-superbird/recipes-core/base-files/base-files/fstab:2`) (V). `opt-overlay-bind:10-17` checks `mountpoint -q /var/lib/bandaid` and, if absent, bind-mounts the rootfs copy `/usr/lib/<vendor>` read-only onto `/opt/<vendor>`; `opt-overlay@.service:4-5,37` orders after `var-lib-bandaid.mount` and only runs when `/usr/lib/%i` exists (V). So a vendor needs a rootfs floor directory, even if it is small.
- Flash behaviour. `mainline-flashthing.bbclass:93-95` adds a second `writeUserArea` at the bandaid LBA when `MAINLINE_FLASHTHING_WITH_BANDAID=1` (the example image base sets it: `examples/.../superbird-kiosk-image-base.inc:7`) (V). The real meta.json of the 2026-11-24 flash zip shows `wic` at lba 0 with `"sparse": true`, then `bandaid.ext4` at lba 2400256 (V, `unzip -p` on the deploy zip). Upstream's release notes list "bridgething bandaid no longer gets clobbered" from 0.1.8 on (`releases/0.1.8.md`); what exactly was clobbered is not stated (U, I: the OTA or adopt path, since a flash writes it by design). Stage OTA moved off bandaid: 0.2.3 "stage daemon ota updates on the data partition instead of the bandaid" (https://bridgething.com/releases/) (V).
- Not found: any design note, issue or ADR explaining the name "bandaid" or why the partition was created (GitHub search of JoeyEamigh/yocto-superbird, bridgething and Nocturne docs; the repo shows 0 open issues). Reading the name as "a patch layer over the immutable root" is an inference (U).

## Project facts checked in the repo

- Geometry knob: `SUPERBIRD_BANDAID_PART_SIZE ?= "192"` (`meta-superbird/conf/distro/superbird.conf:50`) feeds both `files/wic/superbird-mainline.wks.in` (bandaid part line, `--fixed-size ${SUPERBIRD_BANDAID_PART_SIZE}M`) and the build-time headroom check (V). The project checker hard-codes six partitions and 192 MiB (`tr:build/tools/check_image_accounts.py:206,1444`, arg `--bandaid-size-mib` at 1869) (V). The project sets only `SUPERBIRD_ROOT_PART_SIZE = "900"` (`tr:build/build-image.sh:261`) (V).
- Headroom rule: `superbird-headroom-check.bbclass:118-120` requires `data_floor = MIN_EMMC(3600) - (env 8 + 2*boot 64 + 2*root + bandaid) >= boot + root + margin 64`. The class header says only "no room for one ota write on the smallest target eMMC"; the reason for the boot + root sum is not written down (U, I: room for one staged slot payload on data, which matches upstream moving staging to data in 0.2.3) (V for the formula).
- Factory reset: `superbird-factory-reset.sh:2,17` runs `wipefs -a` only on `/dev/disk/by-partlabel/data`, armed by u-boot env `factory_reset=1` (V). It never touches bandaid.
- Does a flash overwrite bandaid: yes (V on the mechanism, I on the consequence). The wic spans the bandaid region (wic file 1,430,275,072 B; 2,400,256 + 393,216 sectors = 2,793,472 sectors = 1,430,257,664 B plus a 17 KiB GPT tail) and is written sparse, which erases the target range first (`docs.rs flashthing fastboot/flash.rs` `write_raw`, sparse branch: "erasing ... before sparse write"), then `bandaid.ext4` is written on top. Any file on bandaid is gone after every full-zip flash. A flash that spares bandaid would need a hand-made meta.json writing only the GPT and slot ranges; not tested, and where the backup GPT ends up on a larger disk is U.
- Does a flash wipe `/var`: same geometry, no. `tr:docs/research/device-settings-spikes.md` row P0.10 records state surviving the week's burn-mode flashes (V, device observation by the project). A geometry change (root 516 to 900) moves the data start, so `/var` is effectively wiped (`tr:docs/research/packages-and-usr-overlay-plan.md` section 2.3, marked inferred there) (I). The wks has no data partition; `superbird-provision` carves it with `sgdisk -n 0:0:0` and `x-systemd.makefs` formats only without a filesystem signature (`tr:docs/research/etc-persistence-options.md` section 0) (V).
- Stable identity without storage: `/sbin/superbird-preinit` derives the machine-id from the efuse serial, stable across boots, slots and reflashes (`meta-superbird/README.md`, superbird-machine-id bullet) (V).
- Entware needs `/opt` at exactly that path: ELF INTERP `/opt/lib/ld-linux-aarch64.so.1`, RUNPATH `/opt/lib`; full toolset 29 MB download, 77 MB installed; feed is unsigned (`tr:docs/research/entware-verification.md` facts 3, 4, 9 and size lines) (V there). Note `opt-overlay` binds `/opt/<vendor>`, not `/opt` itself (`opt-overlay-bind:8`), so Entware needs one small project unit that binds `/var/lib/bandaid/entware` onto `/opt`, or a fork of the script (V for the limitation).
- Mount options: `rw,noatime,sync,nofail`. `sync` makes every write synchronous (slow for opkg's thousands of small files; U how slow). No `nosuid`, `nodev` or `noexec` (V).
- Journald: `SystemMaxUse=128M` on `/var` (`meta-superbird/recipes-core/superbird-base-files/files/journald-superbird.conf`) (V). The kernel cmdline carries `ramoops.pstore_en=1 ramoops.record_size=0x8000 ramoops.console_size=0x4000` but no `mem_address` or `mem_size` (`meta-superbird/recipes-bsp/superbird-extlinux/files/extlinux.conf:8`); whether a reserved-memory region exists in the DTS is U. Ramoops is RAM, so it survives a warm reboot, not a power cut.

## Evaluation of uses

| Idea | Verdict | Cost | Key risk |
|---|---|---|---|
| (a) Host Entware `/opt` | Yes, best use | Small: one bind unit, one floor stub, bandaid recipe | `sync` mount slows opkg; flash resets it to baseline; 192 MiB is a hard cap |
| (b) Secrets and identity | No | n/a | Rewritten by every flash, reformatted by fsck, wiped by rollback; `/var` is the better store |
| (c) OTA .swu staging | No | n/a | Upstream moved staging off bandaid in 0.2.3; 192 MiB is smaller than a slot |
| (d) Frontend or config updated without OTA | Conditional, not now | Medium to high: floor-sync, compat gate, rollback | Version skew, no A/B, seed-once masks OTA, root-run writable code |
| (e) Log or crash dump | No | Small | `sync` mount, shared 192 MiB, no real wear data; ramoops is RAM |
| (f) Recovery or diagnostics payload | No | High | A broken root slot cannot use it; burn mode and slot B already recover |
| (g) Offline cache or preseed | Yes, as part of (a) | Small to medium: a recipe that packages Entware ipks | Unsigned feed means pin hashes at build |
| (h) Writable base for the shelved `/usr` overlay | No | Medium | Same OTA reconcile problem as on `/var`, plus a 192 MiB cap |

### (a) Entware `/opt` on bandaid

Pros. Writable, size-capped and isolated from `/var`: Entware growth cannot eat the `/var` free space that the OTA headroom rule (`data >= boot + root + margin`) assumes. A data wipe (`factory_reset`) leaves it alone. fsck policy makes it self-healing (corrupt means reformat and reseed to baseline, `superbird-fsck.sh:79`, `opt-overlay-bind:20-28`). The ext4 has a 4 MiB journal (`bandaid-image.bbclass:47`). It is already a mounted, fsck'd, nofail partition, so no new partition, no wks fork, no new GPT geometry.

Cons. `sync` mounting (fstab:2) will make `opkg install` of large packages slow; a remount `async` around installs is possible but is a root-run step, or change the fstab option (a base-files change, check the sstate fan-out first, see the skill pitfall on core bbappends). Every full flash resets it to the baked baseline (so installed extras vanish on reflash; same as the `/usr` overlay, and arguably a feature). 192 MiB cap: the whole owner toolset is 77 MiB installed and 29 MiB download (`entware-verification.md`), so peak is about 110 MiB (arithmetic mine), fits, but python venvs or large tools do not.

How. New recipe `thing-revived-entware-bandaid` inheriting `bandaid-image.bbclass` with `BANDAID_VENDOR = "entware"` and a package that installs the Entware bootstrap (and optionally the preseeded ipks, see (g)) under `/usr/lib/entware`. A leaf package ships a small `/usr/lib/entware` stub in the root so `opt-overlay@entware.service` passes its `ConditionPathExists` and has a read-only fallback. Because `bandaid-image.bbclass` copies only `/usr/lib/<vendor>` out of the listed ipks (`:39-41`) the bulk need not be in the root image. One new unit binds `/var/lib/bandaid/entware/opt` (or the seeded dir) to `/opt`, ordered like `opt-overlay@.service` (After `var-lib-bandaid.mount`). Set `MAINLINE_FLASHTHING_BANDAID_RECIPE` to the new recipe (`superbird-kiosk-image-base.inc:8` uses the example's recipe; the project bbappend must override it). The placeholder `superbird-kiosk` daemon and its 217 KB can move into the same ext4 as a second vendor dir, or be dropped with its recipe. Checker: no geometry change, add checks for the unit, the stub dir and the new ext4 contents. Cost: about a day of recipe work plus one build and one flash cycle (estimate, U).

Verdict: do it.

### (b) Secrets and identity (feed key, ssh host keys)

Pros: separate filesystem from `/var`; survives `factory_reset`. Cons: contradicts upstream's disposable design (fsck reformat, rollback `rm -rf`), and the flash rewrites it (wic erase plus `bandaid.ext4`), so it does not survive the exact event the owner cares about. A meta.json that spares bandaid is possible in principle but untested (U) and would need `build/flash-image.sh` to rewrite the zip. `/var` already survives same-geometry reflashes (P0.10), and the machine-id is efuse-derived, so the identity gap is smaller than assumed. Mount is `sync`, not `noexec`, and there is no encryption on any partition (U, nothing found). Verdict: no; keep `/var` and document that a geometry change wipes it. If a secret must outlive a flash, export it off device.

### (c) OTA .swu staging

Pros: protects `/var`. Cons: upstream tried staging on bandaid and moved it to data in 0.2.3 (https://bridgething.com/releases/). A slot payload is hundreds of MiB (the project's content-sized root image is about 487 MiB, `packages-and-usr-overlay-plan.md` section 2.2), so 192 MiB is too small and `sync` writes would be slow. The project OTA design is not built yet (`tr:docs/packages.md:159`). The `superbird-ota` helper streams the file to swupdate (`superbird-ota.sh:16`), and swupdate streaming does not itself require a staged copy (U, not checked in swupdate source). Verdict: no.

### (d) Frontend and `terminal.toml` updated without an OTA

Upstream does exactly this for its own webapps (adopt-daemon, floor-sync, the `builtin-webapp` kind), so the mechanism is proven. Pros: a 5 to 10 MB payload instead of a 900 MiB slot write (though zchunk delta OTA exists in the BSP, `files/delta/sw-description`), fast iteration, no reboot. Cons for this project: (1) version skew: the frontend and `controller-agent` share a wire protocol with golden fixtures, so a hot frontend can disagree with a root-baked controller; you would need a protocol version gate like upstream's per-component version compare. (2) No A/B: a bad frontend update bricks the UI until rollback; upstream hand-rolls `.current/.previous` plus a wipe-to-factory script. (3) Seed-once: after an OTA that ships a newer frontend, bandaid still serves the old one unless floor-sync is built. (4) Writable code run as root: `controller-agent` runs as root (`tr` skill note, unit has no `User=`), so any controller or terminal binary on bandaid is root-writable code outside the signed A/B image; the frontend is only loaded by Chromium, but it speaks to a root daemon over WebSocket. (5) The kiosk URL is `file:///usr/share/superbird-kiosk-default/index.html`; pointing it at `/opt/...` changes `CHROMIUM_KIOSK_URL` and the chromium-kiosk bbappend. (6) `terminal.toml` already lives at `/etc/thing-revived/terminal.toml` and `/etc` is already a persistent overlay on `/var`, so config does not need bandaid. Cost: floor-sync, compat check, rollback, checker changes, tests. Verdict: not now. Revisit only if the signed delta OTA proves too heavy in practice. A cheap middle path is a dev-only bench shortcut (push to `/opt`, point the kiosk at it with a build flag), not a shipped feature.

### (e) Log or crash dump partition

Pros: logs survive a data wipe. Cons: the 128 MiB journal cap already bounds `/var` use (`journald-superbird.conf`); no measurement of eMMC wear from journald exists (U), so the problem is unquantified; bandaid is `sync` and shared with Entware, and upstream treats it as reformat-on-fail, so logs would die with it; ramoops (`extlinux.conf:8`) is RAM, and without a verified reserved region it may not work at all (U). A flash erases bandaid anyway. Verdict: no. If wear matters, set `Storage=volatile` or lower `SystemMaxUse` on `/var`.

### (f) Recovery or diagnostics payload

Pros: tools reachable when the root slot is broken. Cons: nothing can use them. A broken slot cannot mount bandaid without a kernel and init; extlinux boots `root=PARTLABEL=root_${slot}` only (`extlinux.conf:8`), and booting a recovery rootfs from bandaid would need a recovery kernel or initramfs plus u-boot ext4 support, none of which exists (U on u-boot config). Recovery already has two layers: A/B rollback after 3 failed tries and mask-ROM burn mode, which upstream says always works (https://bridgething.com/install/). If the system boots but userland is broken, adb and UART are the diagnostics path. A last-known-good config copy belongs on `/var`, which survives OTA. Verdict: no.

### (g) Offline package cache and first-boot provisioning

Pros: bandaid is rebuilt from the build every flash, so Entware ipks pinned by SHA256 in a recipe `SRC_URI` give a reproducible, network-free baseline that is also the factory floor for reseed. This also addresses the unsigned feed: the baseline is hash-pinned at build, only later `opkg upgrade` trusts the feed over http (`entware-verification.md` fact 9). Cons: the bandaid.ext4 grows and the preseed ipks must be refreshed by hand as the feed rebuilds weekly; old versions move to `archive/` (fact 11), so a pinned URL can rot (U for retention length). Cost: a recipe that fetches named ipks and installs them under `/usr/lib/entware/...`, plus an offline `opkg` source in the opkg.conf. Verdict: yes, folded into (a).

### (h) Writable partition for the shelved `/usr` overlay

Pros: `/usr` upper off `/var`. Cons: overlayfs needs upper and work on one filesystem, so the 192 MiB cap bounds the whole package set; the OTA reconcile problem (stale upper masking a new lower) is identical to `/var` (`packages-and-usr-overlay-plan.md` around line 178); factory reset would no longer clear the upper, which is the opposite of what a reset should do; and `sync` plus per-file whiteouts is a poor fit. Verdict: no. Entware's separate `/opt` tree removes the need for the overlay anyway.

## Ranked recommendation and sizing

1. Entware on bandaid (a plus g). Keep `SUPERBIRD_BANDAID_PART_SIZE` at 192; raise to 256 only if python venvs or heavier toolsets are wanted. This requires no checker geometry change at 192 and only a value change at 256 (`--bandaid-size-mib`). Do the bind-to-`/opt` unit, a floor stub in root, a preseed recipe, and decide `sync` versus `async` after timing an install on device (U).
2. Frontend hot update (d): only conditional, see above. Not recommended in the first iteration.

Data headroom per geometry, floor device 3600 MiB, `required = boot + root + 64` (arithmetic mine from the formula at `superbird-headroom-check.bbclass:118-120`):

| root | bandaid | fixed | data floor | OTA required | slack |
|---|---|---|---|---|---|
| 640 | 192 | 1608 | 1992 | 768 | 1224 |
| 768 | 192 | 1864 | 1736 | 896 | 840 |
| 900 | 192 | 2128 | 1472 | 1028 | 444 |
| 640 | 32 | 1448 | 2152 | 768 | 1384 |
| 768 | 32 | 1704 | 1896 | 896 | 1000 |
| 900 | 32 | 1968 | 1632 | 1028 | 604 |
| 768 | 256 | 1928 | 1672 | 896 | 776 |

Root slot implication. The 900 MiB slot came from the shelved `/usr` overlay and baked-package plan (`packages-and-usr-overlay-plan.md` sections 2.2 and 2.3). With Entware on its own `/opt`, the root only needs content plus growth. The content-sized image is about 487 MiB (same plan, section 2.2; "more after the additions"), so 640 leaves about 150 MiB (30 percent) and 768 about 280 MiB; I would pick 640 or 768, not 900, and 768 if more baked packages are planned. Each step of 128 MiB in root costs 256 MiB of data and raises the OTA requirement by 128 MiB. Any geometry change needs a full flash and, by inference, wipes `/var`, so fix the numbers before the next flash. The `thing-revived-usr` units and `THING_REVIVED_OTA_REQUIRED_MIB` (`tr:build/overlay/recipes-extended/thing-revived-usr/thing-revived-usr.bb:36-37`) read the same sizes, so keep them in sync.

## When removal (or shrinking) is the better call

- If Entware goes to `/var` (for example `/var/lib/entware` bound to `/opt`), bandaid has no remaining job: the project ships agents and frontend in root, and uses bandaid only for upstream's 217 KB placeholder daemon. Then do not keep 192 MiB idle. Cheapest: set `SUPERBIRD_BANDAID_PART_SIZE` to 16 to 32 MiB (a knob, `superbird.conf:50`; update the checker default and `--bandaid-size-mib`), recovering about 160 to 176 MiB for data while keeping every upstream mechanism (fsck, opt-overlay, flash zip) intact.
- Full removal is possible but forks more: a project wks without the part line (`WKS_FILE` is set by the image base, so a bbappend override), `MAINLINE_FLASHTHING_WITH_BANDAID = "0"`, dropping the bandaid recipe from `EXTRA_IMAGEDEPENDS`, the headroom-check formula (it still adds `band_p`, so set the knob to 0 which may fail the ext4 size, U), and the checker's six-partition rule. Boot is safe either way: fstab is `nofail`, `superbird-fsck@bandaid` exits 0 when the device is absent (`superbird-fsck.sh:19-22`), and `opt-overlay` falls back to the read-only factory bind (V by reading). Gain is the last 16 to 32 MiB; cost is a standing divergence from upstream's layout for little. Prefer shrink over remove.
- Entware on `/var` versus bandaid, honestly: `/var` is simpler (no unit ordering on `var-lib-bandaid.mount`, async writes, survives same-geometry reflash), but then Entware growth competes with the OTA headroom and it is wiped by `factory_reset`. Bandaid wins on isolation and a reproducible baseline per flash; `/var` wins on simplicity and reflash persistence. Both are acceptable; I recommend bandaid because the partition already exists and the headroom rule is the scarcer resource.
