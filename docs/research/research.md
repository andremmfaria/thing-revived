## 1. Device Deep Dive

### 1.1 Hardware recap

The basic silicon facts researched here — SoC (Amlogic S905D2, G12A family), RAM/eMMC, display, button/knob/touch counts, and the USB-C gadget/host-mode split — are now the owned content of [`hardware.md`](../hardware.md) (quick-reference) and [`hardware-verification.md`](hardware-verification.md) (live on-device confirmation), both of which have since superseded this document's working notes with real hardware readings. See those for the current numbers; they are authoritative if anything here ever disagrees with them.

One hedge from this research pass is **not** resolved by either of those files and is kept here in full, since it's a genuine two-source conflict rather than duplicated content: **the Bluetooth radio's exact chip identity.** The yocto-superbird BSP README lists the Bluetooth chip as **BCM20703A2** ("BCM20703A2 bluetooth" in `meta-superbird/README.md`). Against that, an independent community hardware teardown (chip physically de-lidded and photographed) identifies the RF chip as **Infineon CYW20706UA2KFFB4G**, which Infineon's own datasheet confirms is the rebrand of **Broadcom BCM20706UA2KFFB4G** (`err4o4/spotify-car-thing-reverse-engineering` issue #31, opened 2024-07-26, photos attached; Infineon CYW20706 datasheet's Broadcom↔Infineon part-number mapping table). BCM20703 and BCM20706 are **confirmed-distinct Broadcom SKUs**, not a rebrand of one another — BCM20703A1/A2 is documented elsewhere as a BT4.1/4.2-only companion chip used alongside separate Wi-Fi silicon (e.g. MacBook Pro 2016 A1707, BCM943602-series cards), a materially different part from the 20706 family. The earlier explanation here ("BCM20703A2 and CYW20703A2 are the same part, Cypress continued the line, so 'CYW20706' was likely a mix-up") is true as far as it goes but does not bridge to CYW20706, a genuinely different number, not a vendor rebrand of 20703. **Confidence: medium-high that the README text says BCM20703A2 (confirmed, it does); genuinely unresolved which chip is actually on the silicon** — whether yocto-superbird's README is a documentation error (e.g. copied from a different Amlogic reference design) or reflects a hardware revision difference from the unit the teardown de-lidded is not settled by any source found, and this is flagged as an open two-source conflict, not resolved in either source's favor. Either way: Bluetooth Classic (BR/EDR) + BLE combo chip, no Wi-Fi silicon on this board.

At the time of this research pass, the exact `/dev/input/eventN` enumeration and scancodes for the 5 buttons, knob rotation, knob click, and touchscreen were all unconfirmed — this section's generic-fallback reasoning (standard `gpio-keys`/`rotary-encoder`/`EV_ABS` Linux conventions) was written to avoid hardcoding guessed values into the implementation plan. **That open question is now closed**: the real event nodes, event types, and keycodes have since been confirmed live on real hardware (`/dev/input/event0` = `gpio-keys` with 7 real keycodes, `/dev/input/event1` = knob rotation via `REL_HWHEEL`, `/dev/input/event3` = touch) — see [`hardware.md`](../hardware.md) for the quick-reference table and [`button-knob-clock-design.md`](button-knob-clock-design.md) for the full design built on top of those confirmed codes. ## 2. Firmware / OS Choice

### 2.1 Major finding: the recommendation has changed since the original brief
The original project context named `JoeyEamigh/nixos-superbird` as the most promising base because of its working Bluetooth PAN support. That is now **outdated**: as of this research date, the `nixos-superbird` README itself states:

> "I recommend using [yocto-superbird](https://github.com/JoeyEamigh/yocto-superbird) instead for better stability and way more performance :)"

This is the same author (Joey Eamigh / Thing Labs) deprecating his own NixOS-based project in favor of a new Yocto-based BSP. **Confidence: high** (primary source, repo README, unambiguous statement).

### 2.2 `yocto-superbird`: new recommended base

Repo: `github.com/JoeyEamigh/yocto-superbird` ("Yocto BSP for the Spotify Car Thing", 14 stars, actively committed, 152 commits at time of research, announced on r/carthinghax under "[Nerd Announcement] yocto-superbird: bluetooth, chrome 147, gpu..."). This BSP was indeed the one ultimately chosen and built — the full account of setting up the build environment, the actual recipe-level customizations made, running/monitoring the build, and the flashing procedure (`flashthing-cli`, Amlogic mask-ROM mode, buttons 1+4) now lives in [`yocto-build-and-flash.md`](../yocto-build-and-flash.md), superseding this section's own build-mechanics notes.

The one fact from this research pass worth keeping here, because it's the gap that drove the risk assessment in §2.4 below and wasn't yet resolved at research time: this BSP's `recipes-connectivity` layer carries BCM20703A2 BT bring-up, but **Bluetooth PAN/NAP networking over this BSP was plausible given the chip and kernel bring-up, but not demonstrated/documented in any README found** at research time — a gap relative to `nixos-superbird`, which explicitly advertised "support for Bluetooth and Bluetooth PAN (tetherless Car Thing, anyone?)" as a named feature.

### 2.3 USB host-mode capability (new finding, high relevance to this project)
`yocto-superbird`'s README documents that the USB-C/OTG port **boots as a gadget but can flip to host mode at runtime**, with a safety mechanism: flipping to host drops the gadget network and adb, so a helper script schedules an **automatic revert after 300 seconds unless confirmed from another link**. Host-mode class drivers (`usb-storage`, `sd-mod`, `exfat`, `cdc-ether`, `r8152`, `ftdi-sio`, `cdc-acm`) are compiled as kernel modules but not shipped by default; a downstream layer opts in via a `linux-superbird` bbappend. **This does not change the "device mode only" USB-C finding for the stock/kiosk use case**, by default the port is still a gadget, but it means, if ever needed, this specific BSP *can* be configured to drive USB peripherals (e.g., a USB Ethernet dongle) at the cost of losing the gadget link unless a watchdog-style confirm step runs. Not required for this project's design (Section 5), but worth keeping in mind for failure-recovery tooling. **Confidence: high** (explicit README section with example commands).

### 2.4 Should you actually use NixOS anyway?
Arguments for sticking with `nixos-superbird` despite the author's own recommendation:
- It explicitly names Bluetooth PAN/tethering as a supported, named feature today; `yocto-superbird`'s README does not make the equivalent claim about BT networking, only about BT bring-up in the kernel.
- Nix's declarative config and `deploy-rs`-based live-push workflow (via the `examples/flake/Justfile`) is a genuinely good fit for "build once, iterate many times on a single appliance," and the maintainer's own template (`nixos-superbird-template`) lowers the Nix learning curve for a single-purpose box.
- `nixos-superbird` is **not abandoned**, it's in a "superseded but still functional" state, not deleted, and the author still explicitly supports its module interface (`superbird.bluetooth.enable`).

Arguments for moving to `yocto-superbird`:
- Author's own stability/performance claim, and it's clearly the actively-developed project going forward (newer, more commits, newer kernel, newer u-boot, chrome 147).
- `linux-superbird-6.6.y` (the kernel `nixos-superbird` depends on) is now **archived** on GitHub ("This repository was archived by the owner on Jul 12, 2026. It is now read-only."), meaning the kernel backing `nixos-superbird` will not receive further updates from upstream. This is a material risk for a project meant to run unattended for years. **Confidence: high**, directly observed on the repo page.
- Yocto gives finer-grained control over exactly which kernel config fragments (e.g., host-mode USB class drivers) ship, which matters if the dual-transport design in Section 5 ever needs USB host mode.

**Recommendation:** Given that `linux-superbird-6.6.y` is archived and its own maintainer points away from it, **do not start a new project on `nixos-superbird`/`linux-superbird-6.6.y` today**. Prototype on `yocto-superbird`'s bare `superbird-bsp-image`, and treat Bluetooth PAN/NAP support as **unverified on this BSP** until you've actually brought up `bluetoothd` + `bt-network`/NetworkManager NAP against it (see Section 3). If BT networking genuinely doesn't come up cleanly on `yocto-superbird`, the fallback is to pull the BT-PAN-specific kernel/userspace pieces from `nixos-superbird`'s BT module as a reference, or run `nixos-superbird` short-term accepting the archived-kernel risk. This is a decision to validate empirically early in implementation, not to assume either way.

### 2.5 Alternative bases considered and rejected
- `bishopdynamics/superbird-debian-kiosk` ("Wall Thing"): stock Amlogic kernel + Debian 11 rootfs + Chromium kiosk. **This is highly relevant prior art** (see Section 4.4) but is explicitly a **two-box architecture**: it requires a host Raspberry Pi Zero 2 W connected via USB RNDIS, because networking on this image depends on the host device, and Bluetooth, while physically present and kernel-supported, is listed under "Available, but not used in this image." It does not meet the "standalone, no permanently attached PC" requirement by itself, though its button-to-backend-action control logic (webUI "simulate button press," light/scene recall) is a directly reusable pattern at the application layer regardless of which OS/kernel you land on.
- `ItsRiprod/DeskThing`: alternative app platform/ecosystem (desktop companion app + on-device web UI), not BT-networking focused, not evaluated further for this document's purposes beyond the input-mapping note in Section 1.2.

## 3. Bluetooth Protocol Deep Dive

### 3.1 Bluetooth PAN / BNEP (Car Thing as PANU, smart-home-controller host as NAP)

Mechanics (standard BlueZ behavior, cross-checked across BlueZ docs, MultiTech's bluez5 PAN guide, and a Purism community forum thread, all consistent):

1. **Pairing** (both sides): run `bluetoothctl` on each side, `agent on`, `default-agent`, `scan on`, `pair <MAC>`, `trust <MAC>`. Trusting is important, an untrusted-but-paired device will stall on the authorization step when it tries to reconnect to the PAN service later (confirmed independently by MultiTech's guide and a live BlueZ GitHub issue, see below).
2. **NAP service on the smart-home-controller host** (the "server" side), two equivalent ways:
   - `bluez-tools`' `bt-network` CLI: `bt-network -s nap pan0 &` starts a NAP server bound to a bridge interface `pan0`.
   - NetworkManager (if the controller host runs NM): `nmcli connection add type bluetooth con-name "PAN-Share" ifname bnep0 bluetooth.type nap ipv4.method shared`, then `nmcli connection up "PAN-Share"`. NM's `ipv4.method shared` automatically runs a DHCP server + NAT-style shared connection on the resulting `bnep0`/bridge interface, this is the simplest path if the controller host is NetworkManager-managed (e.g., most desktop-oriented Linux distros; less common on minimal server installs).
   - If using `bt-network` directly instead of NM, you must bring up `bnep` kernel module (`modprobe bnep`) and run your own DHCP server (e.g., `dnsmasq`) bound to the `pan0`/`bnep0` interface, NM's "shared" method does this for you; raw `bt-network` does not.
3. **Client side (Car Thing)**: `bluetoothctl connect <NAP-server-MAC>` to establish the BT ACL link, then `bt-network -c <NAP-server-MAC> nap &` (as PANU/client) to bring up a local `bnep0` interface that gets a DHCP lease from the NAP side. Static-IP `/etc/network/interfaces`-style fallback is also documented (`iface bnep0 inet static`) if DHCP over BNEP proves unreliable.
4. **Known stability issue, documented in a live upstream bug (medium-high confidence, primary source):** BlueZ GitHub issue `bluez/bluez#297` ("How can I setup a Bluetooth PAN Network programmatically?") describes exactly the failure mode relevant here, a second/reconnecting client pairs successfully but BlueZ reports "no services available" for the NAP profile, requiring a detect-and-retry dance (`connect` again, then retry `bt-network -c`) before the PAN session comes up. This is reported as an ongoing rough edge in BlueZ's PAN/NAP client reconnection path as of comments through mid-2025, not a one-off config mistake. For a wall-mounted appliance that will connect/disconnect many times over months (power cycles, walking out of range, controller host reboots), **this is a real risk to the "just reconnect" assumption for BT-PAN** and should be designed around (retry loop with backoff, not a one-shot connect).

**Overall assessment of BT-PAN/BNEP for this use case:** functionally proven (multiple independent guides, `nixos-superbird` shipped it as a named feature), but it is the **heaviest** option, it drags in BlueZ's NAP profile, bridge/NAT or DHCP server config on the controller host, and a documented client-reconnect edge case. It gives you a full IP link, meaning your application protocol (HTTP/WebSocket/MQTT, Section 4) runs unmodified over it exactly as it would over the USB-CDC-NCM cable link, this is the big advantage: **one IP-based application protocol works identically over both transports**, which is exactly the dual-transport goal in Section 5.

### 3.2 Bluetooth SPP (RFCOMM) or BLE GATT as a lighter alternative

**RFCOMM/SPP:** a classic-BT serial-port-emulation profile. BlueZ exposes it via the `rfcomm` kernel module and `sdptool`/`rfcomm` userspace tools, or directly via BlueZ D-Bus `org.bluez.Profile1` registration for a custom UUID. For a low-bandwidth command stream (JSON lines: `{"event":"button","id":3,"action":"down"}`), RFCOMM:
- Setup complexity: **lower** than BNEP for the transport itself (no bridge interface, no DHCP, no IP stack hop), but you must still pair+trust the two devices via `bluetoothctl` first, same as PAN, and then write a small custom daemon on both ends to open/accept the RFCOMM socket, since there's no off-the-shelf "RFCOMM NAP" equivalent server you just toggle on.
- Reconnection/pairing stability: no BlueZ-upstream issue specific to RFCOMM reconnection was found in this research (vs. the concretely documented PAN/NAP one above), but RFCOMM still rides on the same underlying ACL link and `bluetoothd` pairing/trust machinery, so general BT Classic stability caveats apply equally (see Section 6).
- Latency: lower per-message overhead than BNEP+IP+TCP/WebSocket stacking, since you skip IP entirely, relevant for knob-turn responsiveness, though button/knob events are infrequent and small enough that this is unlikely to matter in practice at human-interaction timescales.
- **Native support in common smart-home controller platforms: none found.** Mainstream home automation backends and their plugin ecosystems are built around HTTP/WebSocket/MQTT; there is no stock integration found that speaks raw RFCOMM or a custom BLE GATT profile as a control-surface transport. ESPHome's BLE patterns (`ble_client`, `esp32_ble_tracker`) are about a backend talking *out* to BLE sensor/beacon devices via an ESP32 proxy, not about a wall-mounted Linux SBC pushing custom command frames to a backend. **Conclusion: RFCOMM/BLE GATT would require a custom bridge daemon on the backend host side regardless, the backend will never "just understand" either transport.**

**BLE GATT:** lower power, lower throughput, connection-oriented with MTU constraints (typically approximately 20 to 512 bytes per write depending on negotiated MTU), good for sensors/beacons, awkward for a bidirectional, chatty JSON command protocol; you'd be building and maintaining a custom GATT service (characteristics for each command/state, notify descriptors for state push) for no protocol-level benefit over RFCOMM, since the device is mains-powered and not battery-constrained. **Not recommended for this project**, BLE GATT's main selling point (power efficiency) doesn't apply to a wall-mounted, always-powered appliance.

### 3.3 Recommendation

**Primary: Bluetooth PAN/NAP (BNEP), not RFCOMM/GATT, with the application protocol running over IP regardless of transport.**

Justification:
- The single biggest design win available here is that **BT-PAN and the USB-CDC-NCM cable link both present as an ordinary IP interface** to the Car Thing's userspace. That means the exact same application-layer client (HTTP/WebSocket to the backend, Section 4) runs unmodified over either transport; you write and test it once. RFCOMM/GATT would instead force you to build and maintain a second, bespoke transport-and-framing layer purely for the BT path, duplicating logic that a standard HTTP/WebSocket stack already gives you for free over IP.
- Common smart-home controller platforms have zero native support for RFCOMM or custom GATT as control-surface transports, so RFCOMM/GATT buys you *less* "skip the IP stack" simplicity than it costs you in "build a bridge daemon from scratch on the backend host, in addition to whatever you'd build for the cable path anyway." PAN/NAP costs you BlueZ/NM config complexity once, on both ends, as a one-time setup, then it's just networking.
- The one real risk (documented BlueZ PAN/NAP reconnect issue, Section 3.1 point 4, and general BT Classic reconnect flakiness, Section 6) is mitigated the same way regardless of which BT profile you pick (watchdog + retry-with-backoff), so it isn't a differentiator in RFCOMM's favor.

**When RFCOMM would actually be the better call:** if you were building this on a battery-powered or severely bandwidth/CPU-constrained microcontroller (e.g., an ESP32 instead of a full embedded-Linux board) where bringing up a full IP+BNEP stack is heavy relative to the device's resources. That is not this device, the Car Thing already runs full embedded Linux with a kernel, so the "skip IP" argument for RFCOMM doesn't pay for itself here.

## 4. Application Protocol / Command Layer

### 4.1 Options compared

| Option | Pattern | Fit for knob/button to backend action |
|---|---|---|
| **Backend REST API** (`POST /api/services/<domain>/<service>`-style endpoint, long-lived token in `Authorization:` header) | Stateless request/response | Excellent for "event happened, call exactly one service." Trivial to implement, trivial to debug (`curl`-able), no persistent connection to manage. Weak for *feedback* (you'd have to separately poll the state endpoint to show status on the touchscreen). |
| **Backend WebSocket API** (`wss://.../api/websocket`-style endpoint) | Persistent, bidirectional | Same "call a service" capability (`call_service`-style message) plus event/trigger subscriptions for live state push, the only backend-native way to get instant feedback (e.g., light brightness changed elsewhere) back onto the Car Thing's optional status screen. Costs you connection lifecycle management (reconnect-on-drop, auth handshake replay) that REST doesn't have. |
| **MQTT + MQTT Discovery** | Pub/sub via a broker, backend auto-creates entities from discovery payloads | Good when you want the backend to treat the Car Thing itself as a first-class *device* with its own entities (e.g., a `sensor.car_thing_battery`, `binary_sensor.car_thing_button_1`) that show up in the backend's UI automatically and can be used in automations/dashboards like any other smart-home device. Two-way: the backend can also publish *to* the device's command topics (e.g., "set backlight brightness," "show this text") if the on-device daemon subscribes. Costs: you now depend on a broker (Mosquitto, typically already present in most non-trivial smart-home setups) as a third component. |

### 4.2 Recommendation for this device

**Primary: the backend's WebSocket API** for the live control path (service calls + state subscription for any on-device status UI), **optionally supplemented with MQTT Discovery** if you want the Car Thing itself to appear as a manageable backend device (recommended for a "nice to have" polish pass, not required for MVP).

Justification:
- Pure REST is the simplest MVP (`fire-and-forget` button press to one POST), and is a completely reasonable *first* implementation, ship that first.
- The stated goal explicitly keeps a "small local status UI on its touchscreen" in scope as a nice-to-have. Only the WebSocket API gives you server-push state updates without polling; if you build the status UI at all, you'll want the WebSocket connection anyway, and once you have it, routing the button/knob commands over the same connection (`call_service`-style messages) is strictly less code than maintaining a second REST client alongside it.
- MQTT Discovery is the right call specifically if the long-term design goal is "the Car Thing should look like a smart-home device inside the backend's own UI, with per-entity automations and dashboard cards for its own buttons," rather than "a dumb remote whose button presses are invisible to the backend's entity model." That is a product decision, not a technical constraint, note it for the implementation plan, don't decide it here.
- Either way, all three options are reachable identically over the cable-IP link and the BT-PAN-IP link (Section 3.3's point), so this choice is orthogonal to the transport decision.

### 4.3 On-device daemon: structural sketch (confidence: reasonable engineering judgment, not sourced from a published reference implementation of this exact device)

Target: 512 MB RAM, Amlogic ARM (aarch64), embedded Linux (Yocto or Debian-derived rootfs per Section 2).

- **Language/runtime:** Python 3 with `python-evdev` (reading `/dev/input/eventN` for knob/buttons/touch) + `websockets` (or `aiohttp` for the REST-only MVP) is the pragmatic choice: fast to iterate, every superbird community project already ships a Python toolchain mentality (superbird-tool, superbird-debian-kiosk's install scripts are all Python), and 512 MB RAM comfortably fits a small asyncio Python service (tens of MB resident, not hundreds) alongside whatever kiosk/browser process (if any) is also running. A Rust or Go binary would be more RAM/CPU-frugal and give you a static single binary (nice for a read-only rootfs/A-B update scheme), and is worth it *if* you're also running a Chromium kiosk on the same box and need to claw back memory, but it's not required to get a working MVP, and the research found no existing Rust/Go implementation of this exact bridge to build on, whereas Python's `evdev`/`websockets`/`aiohttp` ecosystem is mature and exactly matches the skills already demonstrated across these community projects.
- **Structure (regardless of language):**
  1. **Input reader task**: opens the relevant `/dev/input/eventN` device(s) (one for buttons+knob, possibly a separate one for touch), `select()`/`asyncio`-polls for events, normalizes raw evdev codes into an internal command enum (`KNOB_CW`, `KNOB_CCW`, `KNOB_PRESS`, `BTN_1_DOWN`...`BTN_5_UP`, `TOUCH_TAP(x,y)`), buffered through a small debounce layer for the knob (quadrature noise) and buttons (mechanical bounce).
  2. **Transport-agnostic command queue**: the input reader pushes normalized commands onto an in-process queue; it does not know or care whether the output path is REST, WebSocket, or MQTT, or whether the underlying link is USB-CDC-NCM or BT-PAN. This is the seam that makes dual-transport (Section 5) tractable.
  3. **Backend client task**: consumes the queue, maps each normalized command to a configured backend action (a small on-device mapping file: `BTN_1_DOWN maps to light.turn_on(entity_id=light.living_room)`, `KNOB_CW maps to light.turn_on(entity_id=..., brightness_step_pct=+5)`, etc.), and sends it via whichever transport is currently selected (Section 5's failover logic). Holds the persistent WebSocket connection (if used) and handles reconnect-with-backoff.
  4. **(Optional) status/UI task**: if a local touchscreen status UI is built, a lightweight renderer (could be as simple as a full-screen web view pointed at a tiny local Flask/FastAPI page, or a native framebuffer UI) subscribes to the same backend state-change stream the WebSocket client receives and redraws.
- **Config**: backend base URL/hostname, long-lived access token (stored outside of version control, read from a local file with restrictive permissions, never hardcode in the daemon source), and the button/knob-to-service mapping, as a single YAML/JSON file analogous to `superbird-debian-kiosk`'s `buttons_settings.py` pattern (same *idea*, a user-editable mapping file, even though that project's actual file wasn't retrievable in this research, see Section 4.4).

### 4.4 Directly relevant prior art (important, previously unknown to the project context)

`bishopdynamics/superbird-debian-kiosk` ("Wall Thing") **already implements almost exactly this application-layer idea**, today, in production use by its author: its README states plainly, as a working feature: *"Buttons and dial used to control a light and recall scenes/automations/scripts on a smart-home controller."* Its web UI includes a "simulate button press" control for testing the mapping without touching the physical device. This is strong validation that the button/knob-to-backend-service-call pattern works well in practice on this exact hardware, independent of which OS/kernel you choose. **Caveat:** this project's actual button-mapping source file was not retrievable in this research (the exact filename referenced in a third-party YouTube walkthrough, `buttons_settings.py`, 404'd at the expected raw-GitHub path, it may live under a different filename/location, or the walkthrough paraphrased a renamed file); treat the *pattern* as confirmed, but the *exact code* as not directly inspected. Worth cloning the repo locally and grep'ing for the mapping file before writing the on-device daemon from scratch, there may be reusable logic.

## 5. Dual-Transport Design

### 5.1 Core principle
Keep the backend client layer (Section 4.3, step 3) **transport-agnostic by talking to the backend by hostname, never by hardcoded IP**, and let the *network layer*, not the application code, decide which physical link currently carries that traffic.

### 5.2 Addressing
- **USB-CDC-NCM (cable) link:** per `yocto-superbird`'s documented behavior, the device advertises itself over mDNS as `<name>.local` when connected via USB-CDC-NCM, and the backend host reaching *it* works the same way in reverse if the backend host also runs mDNS (`avahi-daemon` on Linux). More importantly for this design: the Car Thing's daemon needs to reach **the backend host**, not vice versa, so what matters is that the backend host is reachable at a **stable name** (e.g., a project-chosen `.local` hostname via its own mDNS advertisement, which many backend platforms' own `zeroconf`/mDNS integration or the host OS's Avahi already provides on most installs) from whichever interface currently carries traffic.
- **BT-PAN (bnep0) link:** gets its address from the NAP-side DHCP server (Section 3.1), typically a private range distinct from the USB-CDC-NCM link's range (which on `nixos-superbird`'s documented setup was `172.16.42.x`; the exact range on the cable link under `yocto-superbird` wasn't published in the README excerpt retrieved and should be confirmed empirically). As long as the backend host's mDNS name resolves correctly from *either* interface (which it generically will, since mDNS multicast is scoped per-link but Avahi/systemd-resolved will respond on whichever link the query arrives on), **the daemon's backend client only ever needs to know the project-chosen `.local` hostname**, never an IP literal, and it will resolve correctly regardless of which transport is currently up. This avoids needing dynamic DNS or hosts-file flipping.
- **Fallback if mDNS proves unreliable over BT-PAN specifically** (plausible, mDNS over `bnep0` bridges is less battle-tested than over Ethernet/Wi-Fi): maintain a static `/etc/hosts` entry pointing the chosen hostname at both known static/DHCP-reserved addresses isn't possible with one hosts entry, so the pragmatic fallback is: **DHCP-reserve a fixed IP for the Car Thing on each link** (one reservation on the NAP-side DHCP pool, one on whatever serves the USB-CDC-NCM side) and have the daemon simply **try the configured backend hostname first, and fall back to a configured backend IP literal** if hostname resolution or connection fails within a short timeout. This is a few lines of retry logic, not a new subsystem.

### 5.3 Transport-selection / failover logic
Recommended policy, in order, re-evaluated on every reconnect attempt (not just at boot):
1. **Prefer the cable** if a USB-CDC-NCM link to a host is currently up (gadget `usb0`/`eth0`-equivalent interface has carrier and an address), cable implies the device is docked/charging and the link is point-to-point, inherently lower-latency and immune to RF interference/range issues.
2. **Fall back to Bluetooth PAN** if the cable interface is down/absent, this is the "wall-mounted, not physically cabled" deployment mode explicitly in scope.
3. **Allow both simultaneously by deployment choice**: nothing about this design prevents running both links up at once (e.g., cabled for power + BT for a second always-on redundant path); the backend-client task should simply attempt its current preferred transport, and on send failure/timeout, retry once on the other transport if it's also up, before queuing/dropping the command. Don't build active load-balancing between the two, for a human pressing a button, "try transport A, then B, in under a second" is plenty; you do not need concurrent multi-path sending.
- **Implementation mechanism:** the simplest robust version of this is a small "link monitor" loop (reads `ip addr`/netlink for carrier state on the two known interfaces, e.g. `usb0` and `bnep0`) that sets a shared "preferred transport" variable the backend-client task reads before each send, this can be a plain Python thread/asyncio task watching `/sys/class/net/*/carrier`, no need for a full network-manager abstraction. A local Unix domain socket between a "link monitor" process and the "backend client" process is a reasonable decoupling if you want the two as separate systemd units, but is not strictly necessary for a single-daemon MVP, don't over-engineer this; a single process with two async tasks and a shared variable is sufficient and simpler to debug.

## 6. Risks

1. **BT Classic PAN/NAP reconnection reliability over long-term use.** Documented concretely: `bluez/bluez#297` describes a reproducible "second/later client sees no services" failure mode on reconnect, requiring a connect-retry dance. **Confidence: high** that this specific failure mode exists in BlueZ; **unconfirmed** whether it specifically affects a PANU client reconnecting to the *same* NAP server after being previously paired (vs. the issue's scenario of multiple distinct clients), worth validating empirically early, since it changes how aggressive your retry/backoff logic needs to be.
2. **General BT Classic disconnect-after-suspend/reconnect flakiness in current BlueZ.** An Arch Linux forum thread (March 2025) documents BlueZ 5.80 regressing Bluetooth reconnection after suspend/resume, with the only confirmed workaround being to **downgrade to BlueZ 5.79**, and "fix in progress upstream" as of the thread's last update. **Confidence: medium**, this is a user forum report, not a BlueZ release-notes confirmation, but it is a live, dated, specific regression report, not vague folklore. **Action for implementation:** pin a known-good BlueZ version in whichever OS image is chosen, and plan to re-test after any BlueZ version bump rather than assuming upgrades are safe.
3. **Pairing persistence across power cycles.** Not confirmed either way for `yocto-superbird` or the archived `nixos-superbird`/`linux-superbird-6.6.y` combination, no README or issue thread found that explicitly states "pairings survive reboot" or documents a `[Policy] AutoEnable=true`-style config for this specific device. Standard BlueZ behavior (pairing keys stored under `/var/lib/bluetooth/`) *should* persist across reboots as long as that directory is on persistent storage (not tmpfs) and not wiped by an OTA/factory-reset mechanism, but given these images use A/B partition schemes with OTA update tooling (`swupdate` for yocto-superbird), it is worth explicitly verifying that `/var/lib/bluetooth` lives in a partition that survives OTA updates and slot switches, not in a partition that gets reset. **This is a concrete, device-specific unknown, not generic BT folklore, flag for on-device testing.**
4. **mDNS resolution reliability over `bnep0` specifically.** No source found either confirming or denying this works well; mDNS/Avahi generally works over bridge interfaces but BT-PAN's `bnep0` is a less common mDNS carrier than Ethernet/Wi-Fi. Mitigated by the static-IP-fallback design in Section 5.2.
5. **Bluetooth support maturity gap in the now-recommended OS base.** `yocto-superbird` documents BT chip bring-up but, unlike the deprecated `nixos-superbird`, does not explicitly document BT-PAN/NAP as a working, named feature. There is a real risk that BT networking needs to be built/debugged from a lower level on `yocto-superbird` than the original project context assumed. **This is the single biggest open risk this research surfaced** relative to the original brief's assumptions.

**Recommended mitigations (general, standard practice, high confidence these are the right category of fix even though none are device-specific sources):**
- Run `bluetoothd` and the application daemon as systemd services with `Restart=on-failure` and a sane `RestartSec`, plus a watchdog (`systemd`'s `WatchdogSec=` with `sd_notify` keepalives from the daemon) so a wedged BT stack or hung daemon self-heals without manual intervention, appropriate for a wall-mounted appliance nobody is going to SSH into every time it glitches.
- Build the retry/backoff logic in the backend-client task (Section 4.3/5.3) assuming BT-PAN reconnects can silently fail on the first attempt (per risk #1), always retry at least once with a short delay before surfacing a connection-down state.
- Keep a physical/remote way to recover the device (serial console pads per `frederic`'s repo, or persistent adb/usbnet per `superbird-tool`'s documented setup) so a bad OTA or wedged BT config doesn't require re-flashing in place on the wall.

## 8. Stock Firmware Internals

Scope: this section is specifically about the **factory firmware as shipped by Spotify**, before any community re-flash, i.e. what you get out of the box, App Version 0.24.107 / OS Version 6.3.29-class builds (the version explicitly named by the primary source below as "factory firmware, device never used/updated"). Community replacement OSes (yocto-superbird, nixos-superbird, superbird-debian-kiosk) covered in Section 2 are *not* this, they are discussed here only where they shed light on the stock image (e.g., `superbird-tool`'s partition/env dumps, which were read directly off factory devices before any modification).

### 8.1 Verdict up front

**This is Amlogic "OpenLinux" (Buildroot-based) embedded Linux, booted through bootloader/update infrastructure that Amlogic reuses wholesale from its Android BSP, not a genuine Android/AOSP device running an Android app.** The AVB2/A-B/vbmeta/dtbo machinery that originally suggested "Android ancestry" in earlier research passes is real, but it lives entirely in the **bootloader and partition layer**, which Amlogic's G12A vendor SDK shares between its "Android" and "OpenLinux" (Buildroot) product lines, picking "OpenLinux" does not mean you also get the AOSP userland; the shared bootloader infra travels along for the ride regardless. The actual rootfs, init system, and application runtime are generic embedded-Linux/Buildroot patterns (SysV-style numbered init.d scripts, Qt-EGLFS framebuffer app, `ext4` rootfs), not Android's `init.rc`/Zygote/APK stack. **Confidence: high**, this is triangulated from Spotify's own public source repos (not a community guess), a U-Boot environment dump taken directly off a factory device, and a primary-source root/exploit writeup, cross-checked across three independent authors (Nolen Johnson/Frederic Basse, bishopdynamics, alexcaoys).

### 8.2 OS family: direct evidence from Spotify's own public repos

Spotify operates a public (if essentially unadvertised) GitHub organization, **`spsgsb`**, hosting the actual source Spotify builds the Car Thing from: `spsgsb/uboot`, `spsgsb/kernel-common`, `spsgsb/platform-external-bluetooth-bluez`, and a fork of `mgoeppner/swupdate` ("Software Update for Embedded Systems"). **Confidence: high**, this is Spotify's own code, not a community reconstruction; the ODS Security Research writeup (Nolen Johnson/Frederic Basse, Oct 2022) states plainly: "U-boot and Linux kernel source code for this device is public but advertised nowhere by Spotify," linking directly to this org.

The decisive detail: the shared branch name across `spsgsb/uboot` and `spsgsb/kernel-common` is **`buildroot-openlinux-201904-g12a`**. "Buildroot" and "OpenLinux" are Amlogic's own SDK/product-line naming for its non-Android embedded-Linux BSP track for G12A-family chips (as opposed to their separately-maintained "Android" BSP track for the same silicon). This is a primary-source naming artifact, not an inference from a guide, Spotify's own repo branch literally says what build track it came from. **Confidence: high.**

Two details initially read as "maybe this is Android-flavored" turn out to be inherited vendor-SDK scaffolding rather than evidence of an Android userland:
- `spsgsb/kernel-common` contains `build.config.cuttlefish.*` and `build.config.goldfish.*` files, these are artifacts of Google's **Android Common Kernel (ACK)** tree (`android-kernel/common`), meaning Amlogic's G12A kernel BSP itself descends from ACK, as Amlogic, like most Android-chipset vendors, maintains one shared kernel tree and branches it per product line (Android vs. OpenLinux). **This confirms kernel *lineage* traces back to ACK, but does not mean the shipped kernel boots Android userspace**, Amlogic strips/reconfigures the same tree for its Buildroot track. **Confidence: medium-high** (direct repo-content observation, interpretation of vendor SDK structure is reasonable engineering inference, not Amlogic's own documentation).
- The U-Boot environment and partition table (Section 8.6) carry Android Verified Boot 2 (AVB2), A/B slots, and `androidboot.*` kernel cmdline variables, again, Amlogic BSP-level scaffolding shared across both product lines, not evidence the rootfs itself is Android. See Section 8.6 for the detailed partition evidence.

### 8.3 Bootloader: Amlogic vendor U-Boot, not custom-from-scratch

Confirmed: standard **Amlogic vendor U-Boot derivative** for the G12A/S905D2 platform, not a Spotify-authored bootloader. Evidence:
- `spsgsb/uboot`, branch `buildroot-openlinux-201904-g12a`, same branch-naming convention as the kernel, i.e. Amlogic's standard OpenLinux SDK U-Boot fork for this chip generation, just checked out and signed by Spotify for their specific board (`board/amlogic/superbird_production/` path referenced by `alexcaoys/notes-superbird`, which also references Spotify's own `aml-user-key.sig` production signing key at that exact path).
- The boot-mode/burn-mode procedure (hold buttons 1+4, Amlogic BootROM mode, `pyamlboot`/`update bulkcmd` over USB) is the generic Amlogic USB-burning/recovery mechanism used across the entire Amlogic SoC family, not something specific to this device, confirmed independently by `bishopdynamics/superbird-tool`, `oddsolutions/superbird-bulkcmd`, and `err4o4`'s and `alexcaoys`'s separate unbrick notes, all using the identical Amlogic `BL2` to `BL33` to "Burn Mode" to `update bulkcmd` sequence documented generically for Amlogic chips elsewhere.
- **Confidence: high** that this is the same family of U-Boot Amlogic ships generically on other G12A boards (i.e., "same lineage," not "literally identical binary", Spotify's build carries their own signing key and board-specific config, which is normal/expected vendor customization, not evidence of a from-scratch bootloader).

### 8.4 Kernel: Amlogic/ACK-lineage Linux, exact version not directly captured in this pass

- **Confirmed lineage, not confirmed exact running version string.** `spsgsb/kernel-common`'s branch name `buildroot-openlinux-201904-g12a` dates the kernel baseline to roughly April 2019, and its tree carries ACK (`android-kernel/common`) ancestry artifacts (`build.config.goldfish.*`/`build.config.cuttlefish.*`). Amlogic's G12A kernel BSPs from that era are typically Linux 4.9-series forks; **this specific pass did not retrieve a direct `uname -r`, `dmesg`, or kernel-boot-log version string from a real factory device confirming the exact version**, the 2019-era dating is inferred from the branch name and known Amlogic SDK release cadence, not read off a device. **Confidence: medium** on the approximately 4.9-era estimate; **flagged explicitly as unconfirmed** for the precise `x.y.z` patch level, verify with `cat /proc/version` or `uname -a` over the UART/ADB root shell methods in Section 8.5 if exact version matters to the implementation.
- Separately and for contrast: the *community replacement* kernel repos target **Linux 6.6.y** (`alexcaoys/linux-superbird-6.6.y`, now archived per Section 2.4) and **mainline v7.x** (`yocto-superbird`'s patch stack, per Section 1.2/2.2), these are new kernels built against the hardware from scratch by the community, **not** forks of Spotify's stock kernel tree. Do not conflate stock-kernel version (medium-confidence approximately 4.9-era estimate above) with the community kernels' versions (confirmed, but irrelevant to "what does stock firmware run").

### 8.5 Init system: SysV/BusyBox-style numbered init.d scripts, not Android init

**Confirmed, primary-source, cross-checked across two independent authors:**
- The ODS Security Research root-access writeup shows the kernel cmdline being rewritten to `init=/sbin/pre-init` (plus `ramoops.*`, `rootfstype=ext4`, `console=ttyS0,115200n8`, `root=/dev/mmcblk0p15`), i.e., the stock boot path invokes a small executable at `/sbin/pre-init` as PID 1, not Android's `/init`. This is a standard embedded-Linux pattern (a thin wrapper binary that does early setup, ramoops/pstore config, mount prep, before handing off to the real init), not an Android-flavored init path. **The exact contents/behavior of `/sbin/pre-init` itself were not directly inspected in this research pass**, flagged as unconfirmed specifics; it is plausibly BusyBox's own tiny `init` applet renamed, or a small custom C binary, but which one is not verified here.
- A separate, independent source (a third-party "Debian Chroot" tutorial video walking through a live ADB root shell on the stock OS) shows the author stopping the stock Spotify app via `/etc/init.d/s95_supervisor.d stop` on the live device. `superbird-tool`'s own repo additionally ships an `S49usbgadget` file meant to be installed at `/etc/init.d/S49usbgadget` on the device. **Both are classic numbered SysV-style `/etc/init.d/S<NN><name>` scripts**, the pattern Buildroot's default BusyBox-`init` + `/etc/init.d/rcS` boot sequence uses (run all `S*` scripts in numeric order at boot, `K*` scripts at shutdown/runlevel change). This is strong, concrete, device-observed evidence the init system is **not** Android's `init`/`init.rc`/property-service/Zygote model, there is no equivalent numbered-`init.d`-script convention in stock Android.
- **Confidence: high** that init is SysV/BusyBox-style numbered scripts, not Android init, two independent primary observations (a root-shell writeup and a live video walkthrough) agree, and this is also exactly what you'd expect given the confirmed Buildroot/OpenLinux lineage in Section 8.2.
- Not confirmed: whether PID 1 itself is literally BusyBox's `init` applet, a bare-bones custom init, or something else, only the numbered-script *convention* it drives is directly observed, not the PID 1 binary's own identity.

### 8.6 Partition layout: Android-standard A/B scheme, but at the bootloader/update layer only

Directly read off a real factory device and published by `bishopdynamics/superbird-tool` (`superbird_partitions.py`, derived from `bulkcmd 'amlmmc part 1'` output against a physical unit, plus kernel boot-log partition offsets quoted in the same file), **primary source, device-derived, high confidence**:

```
bootloader | reserved | cache | env | fip_a | fip_b | logo |
dtbo_a | dtbo_b | vbmeta_a | vbmeta_b | boot_a | boot_b |
system_a | system_b | misc | settings | data
```

This is **unambiguously the standard AOSP A/B seamless-update partition set**, `boot_a/b`, `system_a/b`, `vbmeta_a/b`, `dtbo_a/b`, `misc`, `cache`, `data` are the literal names/roles Android's own A/B update documentation (`source.android.com`) specifies for devices with seamless (Android-style) OTA updates; `fip_a/b` (Amlogic's Firmware Image Package, their bundled BL2+BL30+BL31+BL33 blob), `logo`, and `settings` are Amlogic/Spotify additions layered on top of that same scheme.

A U-Boot environment dump taken directly off a factory device (also published in `superbird-tool`, `stock_env.txt`) corroborates this with boot-control-block (BCB) and AVB2 variables lifted straight from AOSP conventions: `avb2=1`, `active_slot=_a`, `bcb_cmd=get_avb_mode;get_valid_slot;`, `androidboot.slot_suffix=${active_slot}`, `androidboot.selinux=${EnableSelinux}`, `androidboot.hardware=amlogic`, `reboot_mode_android=normal`. These are Android's own boot-control-block/AVB/slot-suffix cmdline conventions, used here purely as **Amlogic's shared vendor bootloader update mechanism**, not evidence that `system_a`/`system_b` actually contain an Android system image. Sections 8.2 to 8.5 establish what actually *runs* once that A/B-selected partition is mounted: a Buildroot-lineage rootfs with SysV-style init, not an Android runtime.

**Net read:** this is the strongest single piece of evidence behind the original brief's "hybrid" hypothesis, and it is real, but it answers "how does the chip vendor's bootloader manage updates/security," not "what operating system does the shipped app run on." Those are two different layers, and conflating them was the source of the original "Android/Linux hybrid" ambiguity. **Confidence: high** on the partition/env data itself (device-derived dumps); **high** on the interpretation that this is bootloader-layer AOSP-convention reuse rather than an Android userland, given Sections 8.2 to 8.5's independent evidence for the rootfs/init layer.

### 8.7 BusyBox: strongly implied by init pattern, not independently confirmed by name

**Not directly confirmed in this research pass.** No `strings`/`binwalk` output, `/bin`/`/usr/bin` directory listing, or `busybox --help`/`busybox | head` output naming BusyBox explicitly on the stock image was located. What *was* found (Section 8.5): the numbered `/etc/init.d/S<NN><name>` script convention, which is the textbook signature of a BusyBox-`init`-driven Buildroot boot sequence, and the overall Buildroot/OpenLinux lineage established in Section 8.2. **Given that lineage and that init pattern, BusyBox being present is the overwhelmingly likely default** (Buildroot's out-of-the-box toolchain essentially always includes BusyBox as the core userland utility set unless explicitly swapped for `util-linux`/GNU coreutils, which is unusual for a 512 MB-RAM, 4 GB-eMMC consumer IoT device where every MB counts), **but this is a strong circumstantial inference, not a confirmed observation, and should be stated as such rather than asserted as fact.** Verify directly with `ls -la /bin/busybox` or `busybox` (no args) over an ADB/UART root shell (Section 8.5's access methods) if this matters for planning.

### 8.8 Userland / app runtime: confirmed Qt + EGLFS, not Android APK, not Electron/Chromium

**Confirmed, primary source:** the ODS Security Research writeup states directly that attempts to run other GUI applications on the stock OS were blocked because "this device utilizes a QT feature called **EGLFS**, which doesn't have a window management system like X11 or Wayland," i.e., the stock Spotify app is a **native Qt application using the `eglfs` embedded-Linux platform plugin**, rendering directly to the framebuffer/DRM surface with no window manager, compositor, or desktop environment underneath it. This single detail is itself strong independent confirmation of the embedded-Linux (not Android) conclusion: Android apps are APKs running inside the Android Runtime (ART) against Android's own `SurfaceFlinger`/`WindowManager` stack, they have no notion of Qt's `eglfs` platform plugin, which exists specifically as Qt's answer to "how do I run a GUI on embedded Linux with no X11/Wayland." **Confidence: high**, this corrects the original research document's framing of "Qt/DirectFB" as a guess (part of the original brief, prior to this pass): it is Qt, confirmed, but the specific platform plugin is **EGLFS, not DirectFB** (DirectFB is a different, older Qt embedded backend; EGLFS is Qt's modern EGL/KMS-based one, consistent with the kernel having a modern Amlogic Mali/DRM GPU driver stack).
- Binary/package format: not independently re-derived in this pass beyond "a native Qt/EGLFS binary", no `.apk`, `.ipk`, or Electron/Chromium artifact was reported by any source reviewed. The app itself is referred to in multiple community writeups as "the Superbird app"/"s95_supervisor"-managed process, consistent with a single native binary launched and supervised by an init.d script (Section 8.5), not a packaged Android application or a browser-engine kiosk app (the Chromium-kiosk pattern is a *community replacement* OS feature, Section 2.2/2.5, not a stock-firmware trait).
