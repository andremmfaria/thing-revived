# Competitor feature reference: Nocturne and DeskThing

This document is a feature and idea pool, not an architecture comparison (that ground is covered in [`architecture-decision.md`](architecture-decision.md) and [`hardware-interaction.md`](hardware-interaction.md)). The goal here is purely to catalogue what the two most relevant Car Thing alternative-firmware projects, Nocturne and DeskThing, actually ship today, so that thing-revived's own roadmap has a grounded set of ideas to pull from rather than reinventing scope from scratch. Each project section is a feature inventory from its own README, release notes, and site. The final section is a deliberately selective synthesis of which of those features are realistic to adapt into thing-revived's own standalone, no-PC, Bluetooth/USB-bridge architecture, and which assume a dependency (a tethered phone link or a desktop companion app) that thing-revived does not have and is not adding.

## Nocturne

Nocturne (github.com/usenocturne/nocturne) is a from-scratch custom firmware image for the Car Thing: a Yocto-based OS plus a Rust on-device daemon (`nocturned`) and a Vite + React web UI, all built from one monorepo. It is Spotify-first and leans on a companion phone app over Bluetooth for its most advanced features.

Core playback (Spotify-first): full Spotify playback control, device switching and Spotify Connect, queue view, preset buttons mapped to playlists or tracks, local-file playback and liking, DJ mix, lyrics (its own Spotify view, plus a phone-media LRCLIB metadata-only path for non-Spotify sources), radio/artist/library/recents home sections, podcasts, and podcast playback speed control. It also ships "Mockingbird," an alternate UI recreating the original stock Car Thing look, selectable alongside the standard UI.

Phone integration (via iAP2/Bluetooth or the Nocturne Companion app): Bluetooth-direct phone pairing with no tether required, native iAP2 telephony for incoming and in-call phone call display (gated behind Nocturne+), phone notifications display using ANCS with per-app icons and a core-team-controlled allowlist (gated behind Nocturne+), Google Maps navigation display on Android (gated behind Nocturne+), a voice assistant with wake-word detection and noise suppression (gated behind Nocturne+), and a phone-media now-playing passthrough for non-Spotify audio sources.

Device and system features: A/B OTA updates supporting full-image, daemon-only, webapp-only, and a combined "bandaid" update, with delta/zchunk support for smaller downloads. The settings screen covers Bluetooth device management, software update, backlight idle timeout, a song-title wrap toggle, a night mode and air-vent-interference alert, factory reset, and an About screen. "Nocturne Connector" is a Wi-Fi bridge (Raspberry Pi, Windows, or Mac) for tether-free use without relying on the phone Bluetooth path.

Monetization: Nocturne Lifetime is a $9.99 one-time purchase, Nocturne+ is $1.99/month; both gate the voice assistant, calls, notifications, and navigation features behind a paid tier.

Nocturne has no smart-home integration, no third-party widgets, no app marketplace, and no plugin architecture. This was confirmed directly against the daemon and UI source: there is no plugin, trait, or module-loader pattern anywhere in the codebase. (Spot-checked against the current usenocturne/nocturne README and release notes as of November 2026; the v4.1.x release series continues the same feature set with performance, OTA robustness, and voice-assistant quality fixes, consistent with the list above.)

## DeskThing

DeskThing (github.com/ItsRiprod/DeskThing, deskthing.app) takes a fundamentally different shape: it is a desktop companion app (Windows/Mac/Linux) that serves a web UI to any browser-capable client device, the Car Thing being one of several supported targets alongside old phones and tablets. Functionality lives in a growing marketplace of self-contained apps built against a published SDK (`@deskthing/types`, scaffolded via `npm create deskthing@latest`), each with its own frontend and backend bundled together, installed and updated from inside the desktop server app or from the deskthing.app/apps catalogue.

Official apps (bundled or one-click installable from the desktop server, per deskthing.app/apps as of November 2026): Local Audio (cross-platform control of whatever is playing locally on the host machine), Spotify App (the primary Spotify playback integration), Weather App and a redesigned "Weather Waves" variant (weather plus a now-playing glance, tuned for the Car Thing's physical buttons), VinylPlayer (a record-player-styled now-playing UI alternative), Image Viewer, Settings Tester (an SDK reference app for the settings API), Game Thing (single-player or two-Car-Thing multiplayer games), Discord App ("the ultimate completely recoded discord app," showing voice channel and call state), and Ultimate Clock. The marketing/showcase page at deskthing.app/showcase/what additionally lists a System Monitor app (CPU, memory, disk, network) and names "Home Assistant: control smart home devices directly from your DeskThing" as one of its headline "Core Applications," but a Home Assistant app was not present in the live official or community app listings pulled from deskthing.app/apps at the time of this research, nor could a standalone GitHub repo for it be found; a 2024 Reddit thread in r/DeskThing asks whether Home Assistant support is coming, suggesting it may be aspirational marketing copy or a removed/renamed app rather than a currently shipping one. Treat the Home Assistant claim as medium confidence: officially advertised as a flagship use case for the platform, but not independently confirmed as a live, installable app right now.

Community apps (third-party, same marketplace, installed as downloadable .zip releases): LyrThing (Spotify lyrics), DeskThing-Timer, DeskThing-GitHub (repo, PR, and issue tracking), DeskThing-MarketHub (stock ticker glance), DeskThing-SportsHub (live sports scores), a second independent DiscordThing, pomodoro-thing, ActionThing (configurable buttons that fire arbitrary HTTP requests to external services, effectively a generic webhook/macro trigger), deskthing-volctrl (a volume mixer), a Sonos web app, StreamThingy (turns the Car Thing into a Stream Deck-style OBS/streaming control surface), a Game of Life toy (LifeThing), and a couple of forked/improved variants of the official weather and local-audio apps.

The repo's own tagline, "The Discord Thing, Trello Thing, The Weather Thing, The Macro Thing, Just not The Car Thing anymore," advertises Discord, Trello, and macro/automation support as headline use cases; Discord integration is confirmed live in the apps list (two independent implementations), and ActionThing is the closest confirmed realization of generic macro/automation support (configurable buttons triggering arbitrary HTTP calls). A dedicated Trello app was not found in the current official or community app listings; the project does maintain an active Trello board at trello.com/b/6v0paxqV/deskthing, but that is DeskThing's own development roadmap tool, not a Trello-integration app for users, so the "Trello Thing" branding appears to be either aspirational, a joke referencing the dev board, or an app that existed in an earlier release and was since dropped. Flagged here as unconfirmed rather than included as a real feature.

Architecturally, DeskThing confirms the desktop-companion-app model: the Car Thing (or any browser client) is a thin display/input terminal that talks over local WebSocket to a desktop server process doing all the real work (Spotify auth, Discord RPC, filesystem access, HTTP calls to third-party services, and so on), and apps are sandboxed, thread-isolated server-side modules with a published TypeScript SDK and a scaffolding CLI, distributed as downloadable zips through a community marketplace rather than an app store with review gating. This is explicitly not something thing-revived will adopt wholesale, since thing-revived's whole premise is removing the PC/desktop dependency entirely, but the catalogue of app *categories* that this architecture has made technically easy to build is useful signal for what users of this class of device actually want: media control variants, chat/social status, productivity trackers (GitHub, stocks, sports, pomodoro), generic webhook/macro triggers, games, and (advertised if not fully confirmed) smart-home control.

## Feature ideas worth considering for thing-revived

The following are concrete, specific features pulled from the two inventories above, filtered to what is realistic given thing-revived's standalone Chromium-kiosk-plus-Rust-bridge-daemon architecture with no phone tether and no desktop companion requirement.

Architecture-agnostic ideas, genuinely portable regardless of how they are wired up:

- Preset buttons mapped to arbitrary actions (Nocturne maps them to playlists/tracks; DeskThing's "Configurable Controls" and ActionThing generalize this to "any button does any function," including firing an HTTP request). For thing-revived this maps cleanly onto the existing hardware-input path in the bridge daemon: a config-driven mapping from physical button/knob events to either a local UI action or an outbound smart-home-controller command, no phone or desktop in the loop at all.
- A dedicated settings screen covering backlight idle timeout, a night-mode/dim toggle, and a factory-reset/About screen (Nocturne ships all of these; this gap has since been closed — see [`settings-menu-feasibility.md`](settings-menu-feasibility.md) and [`button-knob-clock-design.md`](button-knob-clock-design.md) for the settings menu that was built).
- A now-playing / media-glance display as one selectable home screen, decoupled from any particular audio source, the way DeskThing's Local Audio app or Nocturne's phone-media passthrough do it; useful even without Spotify since it only needs whatever media-session metadata is locally available.
- A system/connection status view (DeskThing's System Monitor, adapted) — **narrow this to the genuine remaining gap, not a fresh idea**: the project's now-removed NOC-style dashboard prototype once shipped exactly this for the device's own internals (CPU, memory, disk/eMMC, I/O, Bluetooth adapter state, network interface state, all live; see git history for that implementation). What that prototype did *not* cover, and what's actually left to build here, is specifically **bridge-daemon health and last-command latency** — whether `controller/` itself is alive and how quickly a button/knob event round-trips to the smart-home controller, neither of which that prototype's system-level metrics exposed.
- A smart-home control app/screen is the single most directly relevant idea from either competitor, since it is literally the stated purpose of thing-revived already. DeskThing's own marketing names Home Assistant control as a flagship use case for this class of device (confirm-while-building rather than copy, since the live DeskThing implementation itself could not be confirmed as currently shipping); the actionable takeaway is the UI pattern, not the code: a grid or list of controllable devices/scenes bound to on-screen buttons plus hardware preset buttons for the most-used ones, which lines up directly with the existing smart-home-controller transport work in [`research.md`](research.md).
- Generic macro/webhook triggers (DeskThing's ActionThing pattern) are a natural generalization of "preset buttons mapped to actions": let a button fire an arbitrary outbound call (to the smart-home controller, or to any other local service) rather than hardcoding only playback or lighting semantics.
- An alternate/retro UI skin selectable alongside the primary one (Nocturne's "Mockingbird," recreating the stock Car Thing look) is a low-risk, self-contained feature: a second React theme/route, no new daemon surface required.
- A/B or staged OTA updates with a fallback image (Nocturne's update model) are worth keeping on the radar once thing-revived has more than one persistent deployment to manage in the field, independent of anything UI-related.

Ideas that look appealing but assume an architectural dependency thing-revived deliberately does not have, included here so they are not silently re-proposed later without that caveat:

- Phone notifications, incoming-call display, and navigation passthrough (Nocturne, all gated behind iAP2/ANCS plus a paid tier) assume a tethered phone pairing and an active companion-app relationship with the device vendor's OS; thing-revived's bridge daemon currently targets a smart-home controller over Bluetooth/USB, not a phone, so these would require an entirely separate Bluetooth profile and companion-app surface to even attempt, and are a large scope addition for benefit that is tangential to thing-revived's stated purpose.
- Voice assistant with wake-word detection (Nocturne+) is architecturally possible on-device (it is just audio capture plus a model), but it is a substantial new subsystem (microphone hardware support, always-on listening, a speech model) that has no existing foothold in thing-revived's current daemon and should be scoped as its own research pass if pursued, not treated as a quick add.
- Anything that requires routing through a desktop/PC companion app (DeskThing's Discord RPC, GitHub/stocks/sports trackers, Sonos control, StreamThingy's OBS control) is excluded wholesale: thing-revived's one explicit, non-negotiable design constraint is no PC dependency, so the correct takeaway from these is only "this category of glanceable widget is popular on this class of device," not the DeskThing implementation itself. If any of them (a GitHub/CI status glance, a stocks ticker, a pomodoro timer) are wanted later, they would need to be reimplemented as something the on-device daemon can fetch or compute directly (a local HTTP/API poll from the Rust daemon), never by introducing a required desktop companion process.
- An app marketplace or plugin-loader architecture (DeskThing's core model) is explicitly not recommended for thing-revived at this stage: it is a large amount of infrastructure (SDK, sandboxing, a distribution channel) to build and maintain for a single-user/small-community hobby device, and the main benefit it provides, letting other people's code add new feature categories without touching the core, can be deferred until thing-revived actually has multiple active deployers who want to extend it independently.
