# Review: device account lockdown and on-device user management plan

Reviewed: `docs/research/user-management-plan.md` (draft of 2026-11-22). Reviewer: independent read-only check against the devel checkout (`~/workspace/yocto-superbird-build`, deploy dir `build/tmp/deploy/images/superbird`, image manifest of build 20261122202516), the live device (read-only commands only, nothing written) and this repo. Evidence tags: V = verified by reading a file or running a read-only command, U = unverified or inferred.

## Verdict

GO WITH CHANGES. The security design is sound in outline: stock shadow-utils behind a root controller, one authority group, key-only sshd, a one-time reveal gated by a physical press, guard rails enforced server side. Most device facts check out. But six defects would either break the build, leave the owner locked out of SSH on a bad first boot, or leak the one-time password into the persistent journal, so the plan should not go to implementation as written. The `/etc` overlay stays gated by the T0 spike, which is the right call. The plan is also too large for a first release: ship image hardening, the kiosk account and the first-boot reveal first, then the menu (see Recommended phasing).

## Blockers

Each must be fixed in the plan before any coding starts.

1. The build-id wipe (D10, section 3 step 2, section 5) is inconsistent and unsafe on three counts. (a) It wipes only the overlay upper dir and `state.json`. The SSH key store `/var/lib/thing-revived-ssh/authorized_keys/<user>` and `/var/home/<user>` live outside the overlay and survive, so provision step 2 ("copy the seed key only if the file does not exist") never installs the new build's public key, and the plan's claim in section 5 that "all added users and keys disappear" is false. Worse, a user later created with the same name (and a reused uid) inherits the old key file and old home directory, and `user_remove` (section 7 argv table) never deletes the key file either. (b) The device has an A/B scheme (`slot=a`, `slot_a_tries`, `root_a` and `root_b` partitions, `superbird-slot-ok` units), so an OTA, or a rollback after a failed OTA, flips the build-id between slots and wipes accounts and regenerates the kiosk password each time. Rollback is exactly when the owner most needs a known password. The default answer to open question 6 should not be "reset on OTA". (c) Every dev rebuild resets all users. Evidence: V for the key dir location and the A/B facts (`fw_printenv`, wks file, unit list), V for the plan text. Fix: tie the reset to the creation of the data partition or an explicit account-epoch marker, not to a per-build nonce; make wipe cover keys and homes or make key install overwrite the seed key when the epoch changes; delete `authorized_keys/<name>` in `user_remove` and refuse `user_add` over a leftover home.

2. Degraded mode (D4, section 13) does not deliver what it promises. The plan says that if the overlay fails, root is locked, `kiosk` exists and "key login works". But the key is copied into `/var/lib/thing-revived-ssh/authorized_keys/kiosk` only by `thing-revived-provision`, and that unit has `Requisite=thing-revived-etc.service`, so it is skipped when the overlay fails. On a first boot with a failed overlay mount there is no key file, `kiosk` has hash `!` and no password, and nobody can log in over SSH or console: a reflash is the only way out. Evidence: V by reading section 3 step 5, section 5 and D5. Fix: bake the build key into the read-only rootfs and list it as a second `AuthorizedKeysFile` path (for example `/var/lib/thing-revived-ssh/authorized_keys/%u /usr/share/thing-revived/accounts/%u.authorized_keys`, noting the menu then cannot remove the build key, which is arguably a feature and should be an owner decision), or split key install out from the overlay dependency and make the key install the first step that cannot be skipped.

3. The one-time password would be written to the persistent journal. `controller/src/app/hub.rs` logs every outbound event at info with the full JSON unless `log_policy` returns `Silent` or `TypeOnly`, and the only `TypeOnly` entries today are the Bluetooth passkey events. Nothing in the plan adds `user_bootstrap_secret` and `user_secret` to `TypeOnly`, and the plan's golden test only checks serialization. The journal is persistent on this device (`/var/log/journal` exists, `SystemMaxUse=128M`), group `adm` can read it, and `kiosk` is in `adm` by D2. So the first-boot password would land in flash and be readable by the account it protects. The G6 grep for the password would catch it, but only after implementation. Also `user_list`, `ssh_key_list` and `user_result` log usernames and fingerprints in full, which is a smaller leak. Evidence: V (hub.rs lines for `log_policy` and `info!("{json}")`, journal directory on device). Fix: make the log policy default-deny for the new families (type only), add a test that every `user_*` event is logged type-only, and make `emit_to` use the same policy function. Also keep `debug!("client command: {cmd:?}")` safe by making every new password field a `Secret` (the plan already says this).

4. Task T1 (image recipe) is built on wrong facts about this Yocto release and would fail or silently not work. (a) The release is whinlatter/wrynose (`LAYERSERIES_COMPAT` in meta-meson and meta-swupdate, systemd 259.5, `image.bbclass` valid items list). `debug-tweaks` no longer exists as a feature, so `IMAGE_FEATURES:remove = "debug-tweaks ..."` removes nothing; the insecure features come from `EXTRA_IMAGE_FEATURES = "ssh-server-openssh allow-empty-password allow-root-login empty-root-password serial-autologin-root"` in `kas/base.yml` (V). Removing `allow-empty-password allow-root-login empty-root-password serial-autologin-root` from the final `IMAGE_FEATURES` in the prod image bbappend does work, and it makes oe-core's own post-commands stop writing `PermitRootLogin yes`, `PermitEmptyPasswords yes` and the `--autologin root` into `serial-getty@.service`, and makes `zap_empty_root_password` lock root as `root:*:`. That makes most of the plan's openssh bbappend, autologin drop-in and `usermod -L root` redundant (keep the checks). (b) `/etc/securetty` is already owned by the `shadow-securetty` package (meta-meson `shadow-securetty_%.bbappend`, in the manifest), and the distro uses `package_ipk`, so installing a second `/etc/securetty` from `thing-revived-accounts` is a package file collision. Use a `shadow-securetty` bbappend or a rootfs post-command instead. (c) `pam_wheel.so` does not exist on the device (`/lib/security` lists no `pam_wheel.so`) and `pam-plugin-wheel` is not in the manifest, so the planned `su` restriction `pam_wheel.so use_uid group=sudo` would make `su` fail for everyone but root via `pam_rootok`. Add `pam-plugin-wheel` (sudo.inc even has `PACKAGECONFIG[pam-wheel]` for it). (d) `libpam-runtime` ships `common-auth`, not `libpam`, so the planned `libpam_%.bbappend` is the wrong target (the plan says to confirm this in T1; the manifest answers it). (e) `EXTRA_USERS_PARAMS` with `-p '!'` is fragile because `set_user_group` splits on `;` and spaces and runs `eval flock ... -c`; omit `-p` entirely, since `useradd` without a password writes `!` (U, standard shadow behaviour, confirm in T0). Fix: rewrite the T1 table rows accordingly.

5. Password handling contradicts itself in two places. The section 7 argv table lists `useradd ... --password «redacted-secret» ...`, which either puts a hash or a plaintext password in argv (violating "passwords never reach argv" in the same section and the acceptance criterion) or relies on the controller hashing in Rust (which D6 explicitly rejects). Drop `--password`: `useradd` without it leaves the account locked, and `chpasswd` on stdin sets the real password (the plan already describes that rollback flow). Second, the verifier runs `/sbin/unix_chkpwd <user> nullok`. `nullok` makes an empty hash accept an empty password, which is the exact condition the whole plan removes. It must be `nonull`, and the controller must additionally refuse to verify any account whose reduced shadow entry has no hash. Evidence: V for the plan text, U for `unix_chkpwd` argument semantics (setuid helper present, `-rwsr-xr-x`; the spike T0(b) must confirm `nonull` and the stdin protocol).

6. The headroom analysis (section 9) and the image check script measure the wrong thing. The device root filesystem is a 4 KiB-block ext4 of exactly 516 MiB (block count 132096, journal on, 6604 reserved blocks, 7487 free blocks, i.e. about 29 MiB free) created by wic from `--source rootfs --fixed-size 516M`. The deploy `.ext4` file (483 MiB, 1 KiB blocks, `-m 0`, no journal, 41982 free blocks) is a different artifact built with `EXTRA_IMAGECMD:ext4`, and `IMAGE_ROOTFS_EXTRA_SPACE` and `IMAGE_OVERHEAD_FACTOR` do not size the wic filesystem. So the plan's "483 MiB filesystem, 33 MiB below the partition, 29 MiB hidden in the reserved pool" is wrong in every number, the T1 `dumpe2fs` step reads the deploy file instead of the wic partition, and the 4 MiB gate would check the wrong filesystem. The practical conclusion (room for sudo at 2 to 6 MiB) is probably still right, with roughly 25 MiB real margin, but the check must read the root partition out of the `.wic` (or compare the rootfs tree size against 516 MiB minus mkfs overhead). Evidence: V (`tune2fs -l /dev/mmcblk0p3` on device, `dumpe2fs -h` on the deploy ext4, the wks line).

## Risks ranked

1. Overlay on `/etc` after PID 1 is running. Feasible in principle (overlay built in, lower can be a bind of the same dir, machine-id re-bind is plausible) but it is a late mount over a directory systemd has already read units and fstab from, with journald, udevd, resolved, networkd and timesyncd already running in their own mount namespaces. Unverified: propagation into those namespaces, `etc.mount` unit tracking and the umount order at shutdown (nothing orders the overlay before `var.mount` stop, so `/var` may be busy at shutdown), and unit dependency cycles. T0 must run `systemd-analyze verify` and a real boot, not only an `unshare` rehearsal. The plan never evaluates oe-core's own `overlayfs-etc` class. It mounts in a preinit before systemd, which would be cleaner, but it cannot work here because the data partition does not exist on first boot (`superbird-provision` creates it after udev). That reasoning should be written into the plan, since it is the strongest argument for the late mount. U.
2. Lockout by blind acknowledgement. `user_bootstrap_ack` is a plain button; once pressed the secret is gone, and if the owner misread, mistyped or the screen rendered badly, the only recovery is a reflash (SSH key works but `sudo` and the menu need the password). Make the first successful `user_unlock` or `sudo` the real acknowledgement, or require re-entering the last four characters on the reveal screen before ack. Also the reveal TTL is 15 minutes while SSH key login works from boot, so a headless owner can reboot-loop the password without ever seeing it. Acceptable, but document it.
3. Local unauthenticated WebSocket abuse. Any local process can connect, and with D8 the on-device terminal is itself a local-process source. A global unlock backoff (3 free tries, then up to 15 minutes) lets any local process keep the owner out of the Users menu indefinitely (a denial of service, not a bypass). Make the backoff per connection with a smaller global cap, and rate-limit `user_unlock` only after a failure, never block the physical-press path. The press-gating of the reveal accepts any press within 10 seconds, including an ESC tap meant for something else, so a local process polling `user_bootstrap_reveal` gets the password if the owner presses anything in the window. Bind the reveal to a press that happened on the bootstrap screen (a nonce shown on screen is overkill; at least require the knob push event, not any key).
4. Account side doors. The assignable list contains `input`, `video`, `render`, `dialout` and `plugdev`. `input` allows reading `/dev/input/event*`, which includes a Bluetooth keyboard used to type passwords, so it is closer to root-equivalent for credentials than the plan admits; `video` opens `/dev/dri/card*`. Remove `input` and `video` from the default allow-list (or mark them dangerous and require confirm), and note `adm` plus the persistent journal as a read path to logs (blocker 3). Adding a user to `sudo` is, by design, privilege grant; the guard is the unlock plus confirm, which is correct.
5. Menu guard rails do not bind SSH users. A kiosk admin with `sudo` can run `usermod`, `userdel` or edit `/etc/shadow` directly and bypass every guard. That is inherent to sudo and fine, but the plan should say the guards protect against menu mistakes only, and that root-only recovery from a lost password remains a reflash. Optionally ship a narrow sudoers rule is rejected; do not add one.
6. `userdel` and `usermod` while the target has running processes. `loginctl terminate-user` only ends logind sessions. sshd sessions get `pam_systemd`, but the terminal agent's shells and any `sudo`-spawned process do not, and `userdel` refuses a user with live processes, so `user_remove` and the "lock ends sessions" claim can fail in practice. The `kiosk` terminal restarts its shell under `User=kiosk` even when locked, so locking `kiosk` does not remove on-device shell access. State this and add `pkill -KILL -u` (argv, exact uid) as a final step or return a clear error.
7. Stale copy-up. After an overlay copy-up of `passwd`, `group`, `shadow`, `gshadow`, a newer lower layer cannot add a system user without D10 wiping everything. Prefer reconciling (re-merge system accounts from lower on boot) over wipe, which also addresses blocker 1.
8. `useradd` details. Home creation under `/var/home` needs the parent; tmpfiles creates it, fine. `usermod -U` on a never-set password fails by design. `chpasswd` bypasses PAM when `--crypt-method` is given (shadow behaviour), which is what you want, but then no PAM quality or history applies, as planned. Rounds 65536 on a Cortex-A53 may exceed the 0.3 s target for both `chpasswd` and each `sudo` and unlock check; measure in T0, and note unlock is also on the WebSocket reader path unless it is `Blocking` (the plan does set it so).
9. Knob entry usability. The unlock gate needs the 16-character kiosk password every 5 minutes. The weston on-screen keyboard (already used by Wi-Fi) makes this workable, but it should be listed as a hard dependency for the unlock screen rather than an alternative.
10. Provision unit wiring. `After=` and `Before=` do not pull units in. The plan never states `[Install] WantedBy=` for `thing-revived-etc.service` or `thing-revived-provision.service` (`SYSTEMD_SERVICE` only enables what has an `[Install]` section), and the controller and terminal units only order after them. With `DefaultDependencies=no` the units also need an explicit `WantedBy=sysinit.target` to run at all. Also `Requisite=` fails the provision unit if the etc unit is not yet active, so use `Requires=` plus `After=`, or the ordering race produces a spurious degraded mode.
11. SSH hardening values that do nothing for the stated threat (see corrections) and are still listed as mitigations in the threat model.
12. Chromium 68 vs 69: docs say 69, plan says reported 68. Harmless; keep the stricter ceiling.

## Missing items

- No recovery or stale-state story for removed users' key files and homes (blocker 1).
- No audit trail. Nothing records which admin did what (names only, no secrets). Add a short journal line per mutation with op, target, result and connection id.
- No test that exercises the real image: only parsing of the rootfs. Add a chroot or qemu-user run on the devel host of `sshd -T -f`, `visudo -c`, `pwck -r`, `grpck -r` against the built rootfs tree, and a boot test on the device for `systemd-analyze verify`, `systemd-analyze critical-chain` and a `systemctl --failed` check.
- The image check reads `debugfs` of the deploy `.ext4`. It must read the `root_a` partition inside the `.wic` (or the rootfs work dir), otherwise it checks a file that is not shipped.
- No plan for `/etc/hostname`, `/etc/localtime` (symlink into `/var/lib/timezone`), `/etc/resolv.conf` (symlink to `/etc/resolv-conf.systemd`) behaviour once `/etc` is writable and any root process can drop files there that outlive the next boot and hide lower updates. State the policy (only the four account files and `sudoers.d` are expected in the upper; add a boot-time warning or check if anything else appears).
- No mention that the device already holds an outbound SSH key under `/var/lib/thing-revived/.ssh` (id_ed25519, known_hosts), which `kiosk` cannot read (0700 root) but a future "ssh key management" screen might confuse with user keys.
- Frontend: the plan reuses `frontend/src/wifi/picker-view.js` (50 lines) and says to generalise it, but the 63 character picker limit, the shared `index.html` wrapper and `menu-chart.js` (390 lines) are all single-owner files that T8 and any other frontend work would collide on. Name the owner for `menu-chart.js` and `reducers.js` (T7 owns state, T8 owns the chart) and say who resolves a conflict.
- `docs/architecture.md` needs the `ssh -L ... root@<device>` example changed; the plan lists this. Also `docs/yocto-build-and-flash.md` line 47 ("accepts SSH as root") and `docs/terminal.md` line 80 ("unauthenticated root shell") must change; add them to T10.
- Build script: the key and build-id are written into `files/` of the checkout, and the overlay copy is `cp -a` without delete, so a stale key file can survive in a reused `YOCTO_CHECKOUT`. T2 must overwrite or remove the files explicitly and the sstate hash will change on every run (fine, but say it).
- First-boot clock. The device has no RTC and uses a build-epoch floor; `chpasswd` writes the password-change day into `shadow` (`lastchg`) from that clock. With `PASS_MAX_DAYS 99999` there is no aging problem, but the `useradd` default and `usermod -e 1` use fixed dates, so no issue; note it as checked.

## Recommended phasing

The smallest safe first release is Phase 1, with a spike first.

- Phase 0, spike (T0, report only, about one to two days): overlay on `/etc` on the real image and on the device with owner permission, including `systemd-analyze verify`, shutdown order, machine-id re-bind, a power-cut test; `unix_chkpwd` convention; `useradd` without `-p`, `usermod -e ""`, `usermod -U` behaviour; the 516 MiB wic fs headroom; whether a flash keeps `/var` (flash twice, once with an identical image). Decide overlay vs userdb on that evidence.
- Phase 1, hardening plus kiosk plus first boot. Image: remove the four insecure features, add `sudo`, `pam-plugin-wheel`, sshd drop-in, sudoers, no `nullok`, securetty emptied, usb-debugging flag removed by default, `kiosk` via `extrausers`, build-time key (T1, T2, T3). Controller: only the `provision` subcommand, `OneTimeSecrets`, `Entropy`, a press source, targeted reply path, and three commands (`user_bootstrap_get`, `user_bootstrap_reveal`, `user_bootstrap_ack`) with the matching three events and fixtures, plus the log policy fix and an Origin check. Frontend: one blocking reveal screen. Terminal agent as `kiosk` (D8) can ride along because it is a three-line unit change plus docs. Account changes in Phase 1 are done over SSH with `sudo` and stock tools, which is enough for a single-owner device. This delivers every owner requirement except the Users menu, with roughly a third of the planned code and none of the unlock-session, rate-limit, verifier and key-management surface.
- Phase 2a, menu core: unlock session, list, add (generated password), remove, lock and unlock, reset password, last-admin and system-account guards, session and rate limiter, picker generalisation (T4 to T8 reduced to those commands).
- Phase 2b, extras: group add and remove, group list, SSH key management (the only part needing a real keyboard), assignable-groups policy. Defer anything in the plan that has no owner requirement behind it (the 16 user limits, `too_many`, armed factory-reset documentation) unless it is cheap.

## Required plan edits

- Rewrite D10 and section 5 so the reset is keyed on an account epoch, not a per-build random id; define what happens on OTA, rollback and rebuild; wipe or overwrite the key store and homes together with the overlay, and delete the key file and refuse leftover homes in `user_remove` and `user_add`.
- Fix D4 and section 13 so the build key works with the overlay down: second `AuthorizedKeysFile` path to a baked file, or an install step that does not depend on the etc unit; decide if the menu can remove the baked key.
- Add a log-policy requirement to section 7 and section 8: all new events type-only in `hub.rs`, `emit_to` shares that policy, a test proves no `user_*` event body reaches the log, and `debug!` of commands stays `Secret` safe.
- Rewrite section 4: drop `debug-tweaks`, remove the four features named in `kas/base.yml`, drop the redundant openssh and autologin drop-in (keep as asserted checks), install securetty via a `shadow-securetty` bbappend or rootfs command, add `pam-plugin-wheel`, target `libpam-runtime` for PAM edits, remove `-p '!'` from `EXTRA_USERS_PARAMS`, remove `/etc/usb-debugging-enabled` in a rootfs post-command by default, add `[Install]` sections and fix `Requisite` to `Requires`.
- Remove `--password` from the `useradd` argv row; change `unix_chkpwd ... nullok` to `nonull` and add an explicit no-hash refusal.
- Replace section 9 with the real numbers (516 MiB wic fs, about 29 MiB free, check the `root_a` partition in the `.wic`), and update `check_image_accounts.py` to read it.
