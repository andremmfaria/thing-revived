# Dependency Surface

This document answers a specific question that came up during development: what does thing-revived actually depend on to run, and what could realistically be done to reduce that dependency surface. It corrects two assumptions that turned out to be wrong once checked against the live device, then lays out what the real, remaining dependencies are.

## REVISION (2026-11-16): yocto-superbird is now actually in use

Everything below this note, including the "yocto-superbird: never used" claim, describes the project's state **before** 2026-11-16 and is kept for the audit trail, not as current fact. The device has since been reflashed to `yocto-superbird` for real, deliberately, with sign-off, specifically to get a real systemd init, SSH, and a real Yocto recipe pipeline for custom on-device daemons that stock firmware's Buildroot/`supervisord` setup couldn't support cleanly. See [`yocto-build-and-flash.md`](yocto-build-and-flash.md) for the complete build/customize/flash workflow. This changes several facts the rest of this file (and [`hardware.md`](hardware.md)'s original pass) stated as permanent:

- The OS is no longer stock Buildroot/BusyBox/`supervisord`; it is a Yocto-built, systemd-init image from `yocto-superbird`'s example kiosk layer.
- The userspace is no longer 32-bit `armv7`; it is genuinely 64-bit `aarch64-unknown-linux-gnu` (see [`yocto-build-and-flash.md`](yocto-build-and-flash.md#4-the-cross-compile-target-gotcha-this-bsp-is-genuinely-64-bit)). New on-device Rust components must cross-compile to this target, not `armv7-unknown-linux-gnueabihf`.
- Device access is no longer `adb` (that was always a stock-firmware-only path); the device now enumerates as a USB CDC-NCM network device and is reached over SSH instead (see [`yocto-build-and-flash.md`](yocto-build-and-flash.md#7-talking-to-a-freshly-flashed-device)).
- Supervision is now via systemd `.service` units, not `/etc/supervisor.d/*.conf` entries.

The "one real lever" (Chromium vs. Qt/QML) and the Chromium-69-specific coupling discussed below are **unaffected** by this revision: `yocto-superbird`'s kiosk image still runs Chromium (a much newer build than stock's 2018-era 69), so the architectural choice itself stands; only the OS underneath it changed.

## What we are not actually tied to (original pass, superseded above)

**yocto-superbird**: never used. It was evaluated early as a candidate replacement OS, documented in [`research/architecture-decision.md`](research/architecture-decision.md), but the project pivoted away from it once a real on-device RAM measurement showed stock firmware's existing Chromium kiosk architecture had enough headroom to work without a reflash. Nothing currently running on the device comes from yocto-superbird.

**DeskThing**: the device was running DeskThing's client when this project started, but checking the live filesystem today (`find / -iname '*deskthing*'`) returns zero results, and `/etc/supervisord.conf`'s program list is entirely stock entries (`backlight`, `superbird`, `chromium`, `bluetoothd`, `swupdate`, `earlyoom`) plus thing-revived's own three additions: the controller bridge daemon, the now-removed dashboard's `noc-agent`, and the terminal PTY agent. DeskThing only ever swapped the webapp content at a stock path; it never installed its own service. That content has since been overwritten twice over with thing-revived's own UI and dashboard. There is no DeskThing code or configuration left anywhere on this unit.

## What we are actually tied to

1. **The physical SoC and hardware**: Amlogic G12A/S905D2, the evdev input nodes, the vendor Mali GPU blob, the Bluetooth chip. Fixed by the hardware itself, not something software choices can reduce.
2. **An AVB-disabled bootloader state**: a one time unlock, already done on this unit, documented in [`research/hardware-verification.md`](research/hardware-verification.md). Not an ongoing dependency, and not reversible by any future OTA since Spotify's backend no longer exists to push one.
3. **The stock kernel, Buildroot userland, and `supervisord`**: Linux 4.9.113, Buildroot 2019.02.1, BusyBox v1.36.0. This is a real, permanent OS dependency. Reducing it would mean replacing the OS entirely, which was evaluated and rejected: it costs a full reflash, wipes whatever is currently on the device, and the main alternative candidate has weaker proven Bluetooth support than what this unit already has working.
4. **Stock Chromium 69**: the actual pain point. A separate research pass (see [`research/research.md`](research/research.md) and the stock firmware version inventory discussion) confirmed Spotify never once upgraded this across the device's entire OTA history, from the first factory build through the last update before shutdown. No official newer Chromium build exists for this device's architecture (32 bit ARM with glibc, not a configuration Google ships prebuilt binaries for), so this version is effectively permanent short of a from scratch Chromium cross compile with no known working precedent for this exact target.
5. **ADB over USB**: this is a deployment and debugging dependency only, not a runtime one. Once pushed, the device boots and runs fully standalone via `supervisord`; nothing about normal operation requires a host machine to be attached. See [`getting-started.md`](getting-started.md) for the persistent deployment mechanism that makes this true.
6. **Our own code's coupling to Chromium 69's specific quirks**: the React build uses a non-module IIFE bundle — not because Chromium 69 lacks ES module support in general (modules shipped as far back as Chrome 61), but because a plain `file://` page load never gets a `Content-Type` header, and Chromium enforces strict MIME-type checking for `type="module"` scripts regardless of version (see [`getting-started.md`](getting-started.md)§2). Separately, the now-removed NOC dashboard's frontend (`prototype/dashboard/frontend/app.js`, not the controller bridge daemon's own frontend, which has no equivalent code) used `XMLHttpRequest` instead of `fetch` when reading its metrics file over `file://`, because `Response.status` is always `0` for `file://` URLs on this Chromium version, which makes `Response.ok` permanently false (see [`dashboard.md`](dashboard.md)§3 and [`research/hardware-verification.md`](research/hardware-verification.md)). Both quirks would need to be undone if the project ever moved off Chromium 69. Also unaffected by, and compounding, this version pin: Vite 8/React 19's default build output targets a baseline newer than Chromium 69 regardless of module-vs-IIFE bundle format, so `build.target: 'chrome69'` (see [`getting-started.md`](getting-started.md)) is still required even with the non-module bundle shape.

## The one real lever

Everything above the physical hardware reduces to a single actual choice, already identified and decided once in [`architecture-decision.md`](research/architecture-decision.md), worth restating plainly here: keep Chromium and its 2018 era quirks, or drop Chromium entirely for native Qt/QML and remove the browser engine dependency surface completely, at the cost of losing React or Angular as the UI layer. The project currently keeps Chromium, on the basis that its real measured RAM cost on this hardware is small and the quirks found so far have been fixable.

## What the Qt/QML fallback would actually cost, if revisited

A dedicated research pass checked whether that fallback's downside, losing React/Angular as the UI authoring language, is actually avoidable through existing tooling. It is not. No maintained HTML, CSS, or React to QML translator exists; the one serious public attempt at a JSX to QML project never left a work in progress state, and Qt's own developer mailing list has concluded a general converter is not realistically feasible, since QML's retained mode scene graph and the DOM's box and cascade model are different enough that a faithful translator would mean reimplementing a browser engine's layout logic inside QML, defeating the point of dropping Chromium at all.

What is real: Qt Quick Controls 2 is a mature, actively maintained, embedded proven component library that reduces raw QML boilerplate, and is the correct default if this path is ever taken. KDE's Kirigami and Qt's own Design Studio offer higher level page composition and visual authoring respectively, but both lean toward Qt6 tooling, which raises an unresolved compatibility question on this specific hardware, a 32 bit ARM device on a 2019 era kernel with a vendor Mali GPU blob, the same kind of open question already flagged for Chromium's own GPU path in `architecture-decision.md`. Felgo's commercial tooling was checked directly and found to add no meaningful embedded specific advantage beyond plain Qt.

On a plugin or marketplace style architecture specifically: Qt's own `qmldir` and `QQmlExtensionPlugin` mechanism genuinely supports loading a new page or plugin at runtime from a shared library without recompiling the main binary, and a simpler `Loader` based mechanism can load a plain QML file from disk at runtime with no compiled code at all. Neither Kirigami nor Felgo nor any other found project wraps this into a DeskThing style marketplace or manifest system; that layer does not exist off the shelf and would have to be built in house on top of Qt's real, native mechanism.

**Conclusion, if this path is ever taken:** hand written QML and C++ with Qt Quick Controls 2 as the boilerplate reducer, Qt 5.15 LTS given this hardware's age, and a custom lightweight page loader built on Qt's own dynamic plugin mechanism if extensibility is wanted. No shortcut exists that gives React like authoring on a QML runtime. One more thing worth flagging before picking 5.15 LTS specifically: its commercial support window from Qt (the Qt Company) ended **May 2025**; community/open-source LGPL builds keep receiving security backports for longer, but anyone depending on Qt's own paid support SLA for this hardware's age bracket would need to budget for that gap or move to a newer LTS.
